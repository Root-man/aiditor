# Editor project — architecture sketch & open questions

Oct 12, 2026 · @Boba · revised Oct 13, 2026

## Goals and principles

Build a personal, keyboard-first GUI editor in Rust, organised around **projects** (a primary repo plus other repos and folders) and **workspaces** (everything for one task), with Emacs's buffer/window model as the interaction core. macOS is the target; development happens on both macOS and Linux, so it must build and run on both. It is a private experiment; if it works, it becomes the editor used for daily work.

**Goals**

- ACP client as a first-class subsystem with built-in session management; Claude Code and Codex from day one.
- Emacs-flavoured keybindings and the Emacs buffer/window model as the default. Exact keys are chosen as each feature is built.
- Projects that group several repos and give every agent session the same filesystem scope.
- Workspaces that hold all the files, terminals and agent sessions for one task.
- Built-in terminal, where a terminal is just another buffer; several per workspace.

**MVP feature set**, mapped from current daily use:

| Today in Emacs | In this editor |
| --- | --- |
| projectile | Project commands: create and edit projects, find file across all roots, switch project, grep the project |
| consult | Minibuffer completion for buffers, files, commands and grep hits, with live preview |
| swiper | In-buffer search that lists matching lines in the minibuffer |
| Buffer and window navigation | `C-x b`, `C-x o`, splits, one window configuration per workspace |
| In-buffer editing | Emacs motion, mark, kill ring, registers, keyboard macros, TAB indentation |
| Formatters | Run the language's formatter (`mix format`, `rustfmt`, prettier) as a command; not on save |
| xref / dumb-jump | Jump to definition by grep across the project, no LSP (spec to be decided) |
| compile-mode / `next-error` | Jump to `file:line` from terminal output, grep hits and agent tool calls (spec to be decided) |
| wgrep | Edit grep results in place and write them back (spec to be decided) |
| Multiple cursors | After MVP |
| dired (rarely used) | After MVP |

Languages with first-class support: Elixir (with HEEx), Rust, JS/TS, YAML and Markdown.

**Non-goals**

- Elisp compatibility or running Emacs packages.
- A git UI or Magit replacement. Git runs in terminal buffers, and `git diff` in a terminal is how agent changes are reviewed.
- LSP, multiple cursors and git worktree workflows in the MVP.
- Windows, a TUI frontend, plugins, collaboration, remote editing, more than one frame (OS window).

**Design principles**

1. **Everything is a buffer.** Files, terminals, agent sessions and the message log share one model and one window system.
2. **Everything is a command.** Keys and `M-x` call the same named commands, so every feature is reachable both ways.
3. **Every layer is testable on its own**, and the whole app is testable end to end (see Testing).
4. **One owner of state.** A single-threaded core, running on the UI thread, owns editor state; I/O (agents, PTYs, file watching) and heavy CPU work (grep, fuzzy matching, parsing) run in tasks that talk to it by messages.
5. **Agents use their own tooling, scoped by the project.** The editor gives each agent a working directory and extra roots, then shows what it does: its changes to files that are already open appear in their buffers, and terminals it asks the editor for are terminal buffers.

## Architecture at a glance

Four layers: a thin frontend, one core that owns all state, async services that do I/O, and the outside processes they talk to.

## Core data model

A project defines the filesystem scope; a workspace is the unit of work inside it. Every workspace belongs to exactly one project, and every buffer, terminals and agent sessions included, belongs to exactly one workspace, except the global `*Messages*` buffer (see Workspaces).

| Entity | What it is | Owns / refers to | Survives restart |
| --- | --- | --- | --- |
| Project | A primary repo plus additional repos and folders | Roots, workspaces, default agent | Yes, a TOML file in the editor's config dir, outside the repos |
| Primary repo | The root whose agent config is used: AGENTS.md, CLAUDE.md, MCP server list, agent settings | Path, role line | In the project file |
| Additional root | Another repo or folder the agent gets filesystem access to | Path, role line | In the project file |
| Workspace | Everything for one task, tied to one project | Window configuration, its buffers (files, terminals, agent sessions) | No |
| Buffer | Content plus metadata, independent of any window, owned by one workspace | Content backend, undo history, major and minor modes, markers, text properties (face, invisible with a placeholder, line decoration), file binding or kind | No (auto-save files aside, see Crash safety) |
| Buffer kind | File, Terminal, AgentSession, Messages, Scratch | Kind-specific payload (PTY handle, session id) | No |
| Window | A viewport onto one buffer | Buffer id, point, mark, scroll position | No |
| Window configuration | Split tree of windows (`C-x 2` / `C-x 3`) | Windows, split ratios, selected window | No |
| Frame | The app's single OS window | Shows one workspace at a time | No |
| Agent session | One ACP conversation with one agent process | Agent, project, ACP session id, mode | Index entry only: enough to reload it with `session/load` |

A buffer never knows which windows show it, and a window holds only a buffer id. That separation keeps `C-x b`, `C-x 4 b` and per-workspace window configurations cheap.

A window's point and mark are markers in its buffer, so edits made elsewhere move them. Its first visible line moves only as far as needed to keep point's line on screen; the core does that at redisplay, given the rows the frontend can show.

Buffers have more than one content backend: a rope for file, scratch and Messages buffers, the emulator grid for terminals, and a structured transcript for agent sessions, which the core renders into a rope (see Session buffer under ACP integration).

Each workspace owns its buffers, and a buffer belongs to exactly one workspace, `*Messages*` excepted. Killing a workspace kills its buffers. The same file can have several buffers: a file open in two workspaces has two, kept in sync through the disk. When the file changes on disk (a save from the other workspace, an agent's edit, a `git checkout` in a terminal), every buffer visiting it reverts automatically. The watcher reports every change, the editor's own saves included, and each buffer compares the new disk hash with its own: the buffer that saved sees no change, and the other buffers of that file revert.

If the file changes on disk while its buffer has unsaved edits, the editor does not revert. It marks the buffer as conflicted, shows that in the mode line, and asks you to resolve it the next time you focus the buffer or try to save it. The choices are:

- **Keep mine**: overwrite the disk version on save.
- **Take disk**: revert to the disk version; your unsaved text stays in undo history.
- **Compare**: open a diff of buffer against disk and merge by hand.

Every save also checks the file's hash on disk against the last version the buffer loaded or saved, so a change the watcher missed is still caught before it can be overwritten.

**File handling** (decided in [#45](https://github.com/Root-man/aiditor/issues/45)), with Emacs's defaults where they fit:

- **Encoding.** UTF-8 only. A UTF-8 byte-order mark is kept: stripped on load, written back on save. Other encodings come in M5 ([#155](https://github.com/Root-man/aiditor/issues/155): detect with `encoding_rs`, write back in the original encoding).
- **Line endings.** The first line break in the file sets its ending, LF or CRLF; a file without one is LF. The buffer always holds LF, a save writes the file's ending back, and the mode line shows `(DOS)` for CRLF files.
- **Final newline.** A save adds a newline when the text doesn't end with one, as Emacs's text and prog modes do (`require-final-newline`).
- **Binary files.** A file with a NUL byte in its first 8 KB, or one that isn't valid UTF-8, is refused with the reason in the echo area. A file named on the command line opens as an empty read-only buffer instead, so the app still starts.
- **Saving.** Saves are atomic: write a temp file in the same directory as the target and rename it over the target, after copying the old file's mode to the temp file. A symlink is followed and its target replaced, never the link itself. A file with more than one hard link, or a directory where the rename isn't allowed, is written in place instead, so links stay shared. Owner and group are not copied. Buffer saves and project writes share a process-local gate around the disk check and complete write, including symlink and hard-link aliases. Replacement temps are exclusively created with unique names, and cleanup removes only the operation's own temp. Updates can recreate deleted files; project creation requires an absent path. The gate does not lock out external programs or make in-place writes crash-atomic.
- **Built in [#46](https://github.com/Root-man/aiditor/issues/46).** The file service in `aiditor-services` reads and writes bytes; the core decodes them, and a save encodes the buffer's text snapshot and writes it on Tokio's blocking pool (`files::run`, shared with the headless binary). The hash (FNV-1a 64 of the file's bytes, `buffer::hash`) is taken on load and save; `C-x C-s` refuses with `<path> changed on disk; not saved` when the disk differs, a file that appeared since it was opened as missing included. The final newline is inserted into the buffer, point staying before it. An unmodified buffer is not written (`(No changes need to be saved)`), a finished save says `Wrote <path>`, and a failed one shows its error. Edits made while a save runs stay unsaved. A refused file's empty buffer is read-only: the mode line shows `%%`, and every edit fails with `Buffer is read-only`. The mode line puts `(DOS)` after the buffer name. The in-place fallback is taken only on a permission error, so a full disk fails the save instead of truncating the file. Not yet: a second save while one runs is refused as a change on disk.
- **Built in [#48](https://github.com/Root-man/aiditor/issues/48).** `C-x C-c` (`save-buffers-kill-terminal`) asks `Save file <path>? ` (`Yes`, `No`; typed `yes`, `y` or `no` pick them too) for each modified file buffer, most recent first, then, if any was declined, `Modified buffers exist; exit anyway? ` (`No`, `Yes`); the `Yes` buffers are saved either way, and the app quits once those saves succeed with the buffers unmodified, a failed save cancelling the quit. With nothing modified it quits at once. Closing the window runs the same command instead. Not yet: Emacs's other answers (`!`, `.`, `q`, `d`), quitting from the minibuffer while something is modified, and OS quit paths that skip the window (the Dock's Quit, SIGTERM).
- **Long lines.** Truncated at the window edge in M0, with Emacs's automatic horizontal scroll (`auto-hscroll-mode` set to `current-line`, [#153](https://github.com/Root-man/aiditor/issues/153)): point's line scrolls sideways to keep point visible, and the other lines stay put. Built with Emacs's defaults `hscroll-margin` 0 and `hscroll-step` 0: the line scrolls just far enough to show point, is unscrolled whenever point's column fits the window, and the minibuffer scrolls the same way in the frame's width less its prompt. A column is one char, so tabs and wide chars can still push point past the edge. The cut happens in the display model, which holds only the shown columns (plus one for a partly visible last column), so a long line costs a window's width per redisplay, not its length. Soft wrap built in [#290](https://github.com/Root-man/aiditor/issues/290) (epic [#112](https://github.com/Root-man/aiditor/issues/112)), Emacs-like: every buffer but the minibuffer wraps by default, and `toggle-truncate-lines` switches the current one to the truncation above and back, echoing `Truncate long lines enabled` or `disabled`. As on Emacs's terminal frames a row holds the window's columns less one, the last kept for the marker and the cursor: session buffers and `.md`, `.markdown` and `.txt` files break after the last whitespace that fits (`visual-line-mode`; one more whitespace char may take the last column), else at the width; every other buffer breaks at the width with a `\` in the last column, in the theme's `comment` colour. The core wraps after building the window's lines, so folds, faces and the region need nothing new, and a line is laid out only through the rows the window can show. A window's top is a buffer line and a row within it, and keeping point visible counts rows. `C-n` and `C-p` move by row ([#291](https://github.com/Root-man/aiditor/issues/291)), as Emacs's `line-move-visual`: the goal column is point's column within its row, clamped to a row's last char, or to the line's end on its last row; a truncating buffer moves by lines, and `C-a`, `C-e` and `C-k` stay on buffer lines. Not yet: `C-v`, `M-v`, `C-l` and jumps counting rows (they count buffer lines, then point is kept visible), a prefix argument for the toggle; scrolling counts a wrapped line's rows in buffer chars, so a fold on it scrolls a little further than needed, and a word-wrapped line above point is scanned whole.

**File watching** (decided in [#78](https://github.com/Root-man/aiditor/issues/78)):

- **An event means "check this path".** The watcher's OS backend reports, debounced, only the paths that may have changed. Event kinds (create, remove, rename) are not trusted: FSEvents coalesces them and doesn't pair a rename's two halves. Each buffer visiting a reported path, or a file under a reported directory (inotify reports only the directory when one is renamed or deleted), has its file stat'ed and hashed: a missing file puts the buffer in the deleted state, a hash equal to the buffer's does nothing (its own save), and a different one reverts a clean buffer or conflicts a dirty one. A delete and a create inside the debounce window, as `git checkout` and other programs' atomic saves make, read as one change. When the backend loses events (inotify's queue overflowing, `notify`'s `Rescan` flag), every buffer visiting a file is checked. Each backend hands the core a list of paths, so one backend can later report typed changes instead without touching the other.
- **Deleted on disk.** The buffer stays, with its text and undo history; its disk hash becomes `None` and the mode line shows `[deleted]`. A clean buffer stays unmodified, so `C-x C-c` and killing a workspace don't ask about it, and a file that comes back (switching back to a branch) reverts it like any other change. `C-x C-s` writes the file back without asking, modified or not, since nothing on disk is lost; a save that finds the file gone does the same when the watcher missed the delete. That can recreate a file a branch switch removed, the price of keeping the text.
- **Renamed on disk.** Read as a delete of the old path and a create of the new one: buffers visiting the old path become deleted, and the new path only reaches the file index. Buffers don't follow renames, as in Emacs and VS Code, since FSEvents doesn't pair the two halves.
- **Directories are watched, never files.** A rename over a watched file (another program's atomic save) leaves an inotify watch on the old inode, so a file is watched through its directory.
- **Files no root watch covers.** A visited file outside the project's roots, under an ignored directory (`target/`, `node_modules/`), or in a project with `watch = false` gets a non-recursive watch on its parent directory, shared by the buffers visiting files there and dropped with the last of them.
- **Per platform.** On macOS each root gets one recursive FSEvents watch, and events under ignored paths are dropped. On Linux, inotify needs a watch per directory, so the backend uses the accepted index walk's kept-directory snapshot and watches each directory non-recursively; a directory created later gets a watch unless ignored, then is scanned for files made before the watch was in place. Ignored trees cost no watches, and the watched-files limit counts what is really watched.
- **Coverage recovery.** Accepted index walks republish kept directories even when roots and patterns stay the same. Lost events and reported `.gitignore`/`.ignore` changes refresh filtering and clear previously missed-path suppression, including when the ignore file itself is excluded. Manual indexing and configuration reload reread global excludes; there is no new global-excludes watcher. Directory device/inode checks and backend invalidation reports repair replacements while retaining unaffected registrations. Fresh counts still decide the watch limit; same-scope refreshes retain old eligibility until those counts arrive.
- **Registration failures.** Desired coverage is separate from registrations acknowledged by `notify`. Failed or uncertain changes retry after 1, 2, 4, 8, 16, then 30 seconds, without needing incoming events. The first/changed failure and one recovery go to the echo area and `*Messages*`; identical failures are suppressed. Releasing all coverage cancels retries. Visited files whose root coverage is unconfirmed retain parent-directory fallback. `[unwatched]` continues to describe project eligibility, not backend health.
- **macOS acknowledgment limit.** With notify 8.2.0, batch commit and watch/unwatch discard some stream startup errors, and the native FSEvents stream-start result is ignored internally. Confirmed coverage means success reported by the public API; these hidden failures cannot trigger retry or failure reporting. The accepted scope retains this backend without patching it.
- **Built in [#80](https://github.com/Root-man/aiditor/issues/80).** The watcher service (`aiditor-services`' `watcher`, on `notify`) runs one thread. The core sends it the whole watch set whenever it changes: the roots of every watched project a workspace is bound to, and every file a buffer visits. It reports `Msg::FilesChanged`, the paths collected until 100 ms pass with no new event (1 s at most), each tagged gone, file or directory, plus a rescan flag. The core sends one `FileOp::Check` for the visited files at or under the reported paths (all of them on a rescan). A gone file sets the buffer's `deleted` flag, shown as ` [deleted]` after the name in the mode line, and its disk hash to `None`; a present one clears the flag, leaving the hash for auto-revert ([#81](https://github.com/Root-man/aiditor/issues/81)). For projects with `watch = true`, a reported file that the index lacks or directory holding none of its files (the first time it is reported, so an ignored visited file doesn't re-walk on each save, and an empty directory updates the watched-files count), or a gone path that it holds, re-walks that project's index without echoing, and a rescan re-walks every watched project's index. Ignored means what the index's walk leaves out. Events whose parent is not a directory that walk keeps (nor a visited file's directory) are dropped, and so are existing files that walk leaves out unless a buffer visits them (seen by listing the parent with the walk), and FSEvents' canonical paths (`/private/var`) are mapped back to the watched ones. inotify's open and read events are dropped, so the checks don't feed back. An open `C-x p f` list is not updated by a quiet re-walk.
- **Auto-revert built in [#81](https://github.com/Root-man/aiditor/issues/81).** When a check finds the file with a hash other than the buffer's, an unmodified buffer, in any workspace, is reverted with the diff revert (see Reverting), so the buffer that saved (whose hash is already the file's) is left alone, and a deleted or never-created file that appears reverts its clean buffer too. The revert re-reads the file, so a check that raced a save only starts a revert with nothing to change. It is silent; a failed one (the file turned binary, or vanished before the read) echoes its error as `revert-buffer` does. A modified buffer keeps its text and its hash and becomes conflicted ([#83](https://github.com/Root-man/aiditor/issues/83), below).
- **Conflicts built in [#83](https://github.com/Root-man/aiditor/issues/83).** A check that finds a modified buffer's file present with another hash records that hash as the buffer's conflict, and the mode line shows ` [conflict]` after the name. The conflict ends when a check finds the file back at the buffer's hash or deleted, or when the buffer is reverted or saved. A save refused as a change on disk checks the file, so a change the watcher missed becomes a conflict too. The question is `<path> changed on disk: ` with `Compare`, `Take disk`, `Keep mine`, safe to destructive so `RET` loses nothing. `C-x C-s` asks it every time; focusing the buffer (it becomes the selected window's buffer by any key or workspace switch, checked after each message with no minibuffer open) asks once per disk version, so flipping between `*Diff*` and the buffer while merging doesn't nag, and a conflict arising in the selected buffer waits for the next focus or save instead of opening a prompt mid-typing; `M-x resolve-conflict` asks any time. Keep mine makes the conflicting version the save's base, so the save overwrites it (and from `C-x C-s` saves at once); a file changed again since is still refused. Take disk is `revert-buffer`, one `C-/` from the unsaved text. Compare is `diff-buffer-with-file`, leaving the conflict. Not yet: `C-x C-c`'s and workspace kill's save prompts don't ask, so a conflicted buffer answered `Yes` there is refused and cancels the quit.

**Reverting** (decided in [#79](https://github.com/Root-man/aiditor/issues/79)): a revert applies a diff instead of replacing the text, so point, mark and markers stay with their text. The file service reads and decodes the file and diffs it line by line against a snapshot of the buffer (`similar`, `buffer::revert`); the core applies the changed hunks as one undo group, past read-only, so one `C-/` brings the old text back, and the buffer ends unmodified with the file's hash, line ending and BOM. A marker on an unchanged line keeps its line and column; one inside a changed hunk goes to the hunk's start. A diff that arrives after the buffer was edited or killed is dropped. Formatter runs are to apply their output the same way. `M-x revert-buffer` reverts the current buffer, asking `Revert buffer from file <path>? ` only when it is modified, as Emacs's `revert-buffer-quick` does; it says `Buffer does not seem to be associated with any file`, `File <path> no longer exists` or why the file can't be visited, leaving the buffer as it was. Not yet: char-level diffs inside changed lines, a key (Emacs's `C-x x g`).

**Diff against disk** (built in [#82](https://github.com/Root-man/aiditor/issues/82)): `M-x diff-buffer-with-file` compares the current buffer with its file, as Emacs's command of that name. The file service reads and decodes the file as a revert does and renders a unified diff with `similar` (`buffer::unified_diff`): the file is the old side (`--- <path>`), the buffer the new (`+++ <buffer name>`), with three lines of context. It fills the workspace's read-only `*Diff*` (major mode `diff-mode`, refilled each run, no undo) and shows it in another window without selecting it, splitting a lone window, as `display-buffer` does. No differences says `No differences`; no file, a missing file and a binary one get `revert-buffer`'s messages. An answer for a killed buffer, or one arriving while another workspace is current, is dropped. Line-ending and BOM differences don't show, since both sides are decoded. Not yet: colors for added and removed lines, jumping from a hunk to its source line, `*Diff*` shown when the answer arrives with the minibuffer open (it is filled, for `C-x b`).

## Projects

A project is a TOML file in the editor's config dir that lists a primary repo and additional roots, each with a one-line role.

- **Commands.** Create a project, add or remove a root, edit a root's role line, set the default agent and watching, open the project file for editing. All available as keys and through `M-x`. (Built in [#58](https://github.com/Root-man/aiditor/issues/58): `project-create` (`C-x p c`), `project-add-root` (`C-x p a`), `project-remove-root` (`C-x p r`), `project-set-role` (`C-x p l`), `project-set-default-agent` (`C-x p d`, empty text removes it), `project-open-file` (`C-x p o`) and `project-save` (`C-x p s`). Built in [#191](https://github.com/Root-man/aiditor/issues/191): `project-set-watch` (`C-x p w`) asks `Watch: ` with `true` and `false`, the current value selected, and refuses other text. Unwatched projects show `[unwatched]` only in ordinary windows displaying file-backed buffers. Fileless buffers such as scratch, `*Messages*` and `*Workspaces*` omit the label. Every command but create asks first for a project by name (workspaces bind one since #64, but the commands still ask), the first of equal names winning. A directory prompt lists only directories, the one typed first as `./`, and `RET` returns the selected one (`TAB` enters it), so `RET` right away takes the starting directory; a relative one is taken from the buffer's directory and a trailing `/` dropped. An edit is checked as a loaded file is and rewrites the file in place with `toml_edit`, changing only what differs, so comments and layout stay; it is refused, writing nothing, when the file on disk is no longer the text last read or written (`C-x C-r` reloads). Create and save write `projects/<name>.toml`, refusing a taken name, an existing file, and a name with `/` or a leading `.`. An ad-hoc project is edited in memory until `project-save`. Not yet: projects reload when their visited file is saved, so a hand edit needs `C-x C-r`; the role prompt does not start with the current role.)
- **File format** (built in [#56](https://github.com/Root-man/aiditor/issues/56)). Each project is a `*.toml` file in `projects/` under the config dir:

  ```toml
  name = "aiditor"
  default_agent = "claude"        # optional
  watch = true                    # optional, defaults to true (#191)
  max_watched_files = 10000       # optional, overrides settings.toml (#192)
  ignore = ["*", "!notes/"]       # optional, gitignore syntax (#190)

  [env]                           # optional, strings set for the project's processes (#269)
  MIX_ENV = "dev"

  [primary]
  path = "/Users/me/Repos/aiditor"
  role = "The editor itself"

  [[roots]]                       # zero or more
  path = "/Users/me/Repos/zed"
  role = "GPUI source, read only" # optional, empty by default
  ```

  Every file is read at launch and again on `C-x C-r`. Saved entries reconcile by their absolute project-file paths and retain a session-local identity when their name changes; ad-hoc entries keep their identity too, including when saved. A missing or invalid saved file retains its last valid definition while a workspace is bound to it, then releases its index when the last workspace dies. Reappearance at the same path updates that identity; renaming the file creates a distinct entry without guessing a rename. Duplicate names retain first-match command resolution in deterministic order: existing ad-hoc entries, valid saved files in filename order, then retained bound definitions in prior order. Multi-step operations retain the selected identity; a superseded project-write success triggers a fresh reload instead of replacing a newer definition ([#64](https://github.com/Root-man/aiditor/issues/64)). A file is rejected when it is not valid TOML, has an unknown key or a wrong type, an empty name, a path that is not absolute or not a directory, a root that is the same as or inside another root of the project, a role on more than one line, or an `env` value that is not a string, a variable name that is empty or holds `=` or NUL, or a value holding NUL; the echo area and `*Messages*` show `project <file>: <reason>`, and the other files still load. The core parses and checks the text through the settings module; `aiditor-services` lists the files and checks the paths exist. A `default_agent` that names no registered agent is reported the same way, but the project still loads and keeps the value ([#278](https://github.com/Root-man/aiditor/issues/278)). Not yet: duplicate names are not caught.
- **Roots and folders** (decided in [#57](https://github.com/Root-man/aiditor/issues/57)):
  - **Within one project**, roots never overlap: a root that is the same as or inside another, the primary included, rejects the file with `project <file>: <inner> is inside <outer>`. Find-file, grep and the watchers then see each file once, under one role line. Paths are compared as written, so symlinks and `..` are not resolved.
  - **Across projects**, roots may be shared or overlap (`~/Repos/zed` in several projects): every workspace is bound to one project, so a shared root is never ambiguous, and nothing is checked across files.
  - **A folder without a project** (named on the command line, [#64](https://github.com/Root-man/aiditor/issues/64); an open-folder command was dropped in its review, since the command line and `project-switch` cover it) gets an ad-hoc project held in memory, with the folder as primary and its name as the project name, and a workspace for it. Nothing is written until a save-project command ([#58](https://github.com/Root-man/aiditor/issues/58)) writes it to `projects/`.
- **Launching without a project** (decided in [#189](https://github.com/Root-man/aiditor/issues/189), built in [#64](https://github.com/Root-man/aiditor/issues/64)). Every workspace has a project, so every launch resolves to one, as Emacs's `project-current` does:
  - **A file on the command line** opens in a workspace of the first loaded project one of whose roots contains it. With none, it gets an ad-hoc project at the nearest enclosing git repo (a directory holding `.git`), or at the file's own folder outside any repo, named after that directory as an open folder is.
  - **No argument** gives a workspace on an ad-hoc project whose primary is `$HOME`, with its scratch buffer, whatever the working directory: from the macOS Dock or Finder it is `/`. A welcome dashboard with recent files and projects comes later ([#193](https://github.com/Root-man/aiditor/issues/193)).
  - **Watching and indexing a large project.** Built in [#191](https://github.com/Root-man/aiditor/issues/191): the project file has an optional boolean `watch` key, true by default. An ad-hoc project at `$HOME` defaults to false; other ad-hoc projects default to true, and `project-save` retains the setting. An unwatched project's index refreshes only through `project-index`, its first finder use, or settings reload, and its open files are still watched through their directories (see File watching). Gitignore-style `ignore` patterns in the project file, a `.ignore` file in a root too, narrow what the index, grep and the watcher see, an allow-list included (`*`, then `!notes/`) (built in [#190](https://github.com/Root-man/aiditor/issues/190): one top-level list for the project, each pattern matched relative to each root, applied on top of `.gitignore`, `.ignore` and git's global excludes, so a pattern can't bring back a file they leave out. Unlike git, the last pattern matching a path or any directory above it within the root decides, so `!notes/` keeps everything under `notes/` though `*` matches those files by name, and a later `notes/*.tmp` still leaves some out again; patterns that only exclude behave as in a `.gitignore`. `aiditor-services` compiles every pattern when a project file loads or is written, so a bad one (`[z-a]`) rejects the file as `project <file>: ignore pattern "[z-a]": <reason>`; git's leniency stays, an unclosed `[` being literal. Project commands leave the key alone; a hand edit takes effect after `C-x C-r`, which now re-walks every indexed project quietly, so the finder follows edited roots and patterns too. A root shared by projects with different patterns is watched wherever any of them keeps a directory.) Built in [#192](https://github.com/Root-man/aiditor/issues/192): `max_watched_files` in `settings.toml` defaults to 10000; the same optional nonnegative integer in a project file overrides it. Before adding root watches, an asynchronous index walk counts kept files and directories across all roots, after every ignore filter. Either count over the limit refuses all that project's root watches, shows `[unwatched]`, and explains the counts and `max_watched_files` in echo and `*Messages*` once per changed refusal. Directories include each root, so zero disables root watching even for an empty project; counting directories as well as files bounds sparse Linux inotify trees too. Visited-file directory watches, manual indexing and first-use finder indexing work as with `watch = false`; automatic index refresh stops while refused. A successful reindex, settings reload or project edit reevaluates eligibility, so raise the limit or remove files and run `project-index` to resume watching. The counts belong to the walked roots and ignore patterns: a re-walk of the same ones (a role edit, `C-x C-r`) keeps them, and the root watches, until it answers, while changed roots or patterns leave the project unwatched until their walk answers. Counts are snapshots, not a system-wide inotify quota; directory creation can briefly add watches before the recount finishes. With patterns, `$HOME` can be narrowed enough to watch.
  - The launch workspace `default`, bound to no project, that [#62](https://github.com/Root-man/aiditor/issues/62) started with went away in #64.
- **Switch project** (decided in [#59](https://github.com/Root-man/aiditor/issues/59), built with the workspace commands in [#64](https://github.com/Root-man/aiditor/issues/64)) prompts for a project with completion, then shows that project's most recently shown workspace, or creates a workspace for it and shows that when it has none. It never asks a second question: another workspace on the same project comes from New workspace.

## Workspaces

A workspace is everything related to one task: its file buffers, terminal buffers and agent sessions, laid out in its own window configuration. Creating a workspace asks for a project with the active workspace's project selected by default, and the workspace stays bound to its session-local identity across renames, duplicate names and missing/invalid definitions. Project-name changes update its label without renaming the workspace or scratch. Active and inactive configurations use the same `Windows` representation, retaining selected windows, splits, markers, marks, scroll and jump history.

- **Ownership.** Every buffer belongs to the workspace it was created in. Opening a file that is already open in another workspace creates a second buffer for it here.
- **`*Messages*` is global** (decided in [#61](https://github.com/Root-man/aiditor/issues/61)): one for the app, owned by no workspace, since it collects output from everywhere. Every workspace's buffer list and switcher include it, any workspace's window can show it, and killing a workspace leaves it alone. It is the only global buffer.
- **New workspace.** Starts with one empty scratch buffer.
- **Killing a workspace** kills every buffer it owns, terminals and session buffers included. The agent sessions stay in the session index and can be resumed in another workspace of the same project.
- **Built in [#62](https://github.com/Root-man/aiditor/issues/62)** (the core model; commands come in [#64](https://github.com/Root-man/aiditor/issues/64)). A workspace holds its project by name, since reloads replace the project list. The editor started with one workspace, `default`, bound to no project, until #64 replaced it with the launch rules decided in [#189](https://github.com/Root-man/aiditor/issues/189) (see Projects). Each buffer is owned by the workspace current when it was made, `*Messages*` by none. A file is reused only within the current workspace, so a second workspace gets `a.txt<2>`: buffer names stay unique across workspaces. A new workspace becomes current and shows its `*scratch*` in the selected window. Killing the current workspace makes the one after it current, or the one before when it was last, and the sole workspace can't be killed (`Attempt to delete the sole workspace`). A killed buffer's windows show a buffer of their own workspace (the current one until #63) or `*Messages*`, never another workspace's. `C-x k` refuses `*Messages*` and every workspace's `*scratch*` (`Can't kill <name>`), marked by an `unkillable` buffer flag rather than by name; killing a workspace still kills its scratch. (#64's kill command asks about modified buffers.)
- **Built in [#63](https://github.com/Root-man/aiditor/issues/63).** Each workspace keeps its own window configuration: the split tree, each window's buffer, point, mark and scroll, and the selected window. Switching shows it as it was left, and a new workspace starts with a single window on its `*scratch*`. Windows of a workspace that is not current keep their points and marks as markers, so edits made meanwhile move them. A killed buffer is replaced in every workspace's windows by that workspace's most recent buffer or `*Messages*`. Switching closes an open minibuffer, cancelling its prompt. The switch commands come in #64.
- **Built in [#64](https://github.com/Root-man/aiditor/issues/64).** The commands live under `C-x t`, Emacs's tab-bar prefix: `workspace-new` (`C-x t 2`) prompts for a project with the active project selected (accepting it retains the project identity even with duplicate names), then a name, refusing a taken one; a blank name names it after the project, `<2>` when taken; `workspace-switch` (`C-x t RET`) lists the others most recently shown first and the current one last, so `RET` alone goes back; `workspace-next` and `workspace-previous` (`C-x t o`, `C-x t O`) cycle in creation order, wrapping, a count moving that many; `workspace-rename` (`C-x t r`) renames the current one, refusing an empty or taken name; `workspace-list` (`C-x t l`) opens a temporary read-only `*Workspaces*` tree (see below); `workspace-kill-current` (`C-x t 0`, Emacs's `tab-close`) kills the current one and `workspace-kill` (`C-x t k`) asks which, listing the current one first; both refuse the sole workspace before asking anything, then asks `C-x C-c`'s questions about that workspace's modified file buffers only (`Modified buffers exist; kill anyway? `) and kills once the chosen saves succeed. Each workspace's scratch is `*scratch*<name>`, renamed with the workspace, so every scratch name says whose it is (tests pin the launch workspace's name to `main`, since it otherwise follows `$HOME`). `project-switch` (`C-x p p`) shows the project's most recently shown workspace or makes one. A folder on the command line takes the first saved project one of whose roots contains it, else a new ad-hoc project at the folder (named after it, `<2>` when taken). Ad-hoc projects are matched only by their primary, so the `$HOME` project doesn't take every folder. A launch file's git repo is the nearest ancestor holding `.git` (a directory or a worktree's file); the ad-hoc `$HOME` project defaults to `watch = false` ([#191](https://github.com/Root-man/aiditor/issues/191)). Not yet: an ad-hoc project stays after its last workspace is killed; a quit started while a kill waits on its saves takes over the wait.
- **Outside files.** A workspace can open files from outside its project. What the agent may touch is set by the project roots and the session's approval mode, not by what is open.
- **Lifetime.** Workspaces live until killed or until the app quits; they are not restored on the next launch.
- **Switching buffers.** `C-x b` and the consult-style switcher list the current workspace's buffers. (Built in [#66](https://github.com/Root-man/aiditor/issues/66): `C-x b`, `C-x 4 b` and `C-x k` complete over and find only the current workspace's buffers and `*Messages*`. A name only another workspace has counts as new, so `C-x b a.txt` there makes an empty `a.txt<2>` here and `C-x k a.txt` fails with `No such buffer a.txt`. `C-x b`'s completion is the switcher until a consult-style one comes.)
- **Workspace list.** `C-x t l` and `M-x workspace-list` select a read-only, fileless `*Workspaces*` buffer in the current window. It groups projects by identity, showing their names (and primary roots for duplicate names), workspaces in creation order within each group, and each workspace's listed owned buffers in name order. Projects follow their first workspace's creation order. Scratch and file buffers appear; internal buffers, workspace lists themselves and the global `*Messages*` do not. The current workspace is marked `*` and initially selected. `n`/`p`, `C-n`/`C-p` and arrows move only between workspace rows, stopping at the ends; `RET` dismisses the list and switches the whole workspace using its saved layout. Project and buffer rows are informational. `q`, `C-g`, or accepting the current workspace dismisses the list through normal buffer-kill replacement, retaining the split structure. Each workspace reuses its own list buffer until dismissed; running the command again refreshes its snapshot. An obsolete workspace row reports `No such workspace`. No project/buffer activation, folding or live refresh.
- **Commands.** New workspace (prompts for project, defaulting to the active project), switch, next/previous, rename, kill, list workspaces. All available as keys and through `M-x`.
- **Display.** The frame shows one workspace at a time. The strip is the window title (decided in [#65](https://github.com/Root-man/aiditor/issues/65)): `<buffer>[ *] | <workspace> | <project>` for the current workspace, so it names the current one only and `workspace-list` lists them all.

Emacs has part of this. Since Emacs 27, `tab-bar-mode` gives each tab its own window configuration, but buffers stay global. Packages such as tabspaces and perspective.el add per-tab buffer lists, and tabspaces ties tabs to projects. A workspace here is that combination built in, with ownership of every buffer, terminals and agent sessions included.

## Commands and keymaps

Copy Emacs's model, not just its key chords: named interactive commands, layered keymaps resolved by a key-sequence trie, and a minibuffer for every prompt. Bindings are Emacs-flavoured; exact keys are settled as each feature is built.

- **Command registry.** Each command has a name (`find-file`, `workspace-new`, `agent-send-region`), an argument spec (prefix arg, region, prompted string), and a handler `fn(&mut Ctx, Args) -> Result`. `M-x` lists them all with fuzzy completion. (Decided in [#20](https://github.com/Root-man/aiditor/issues/20): every call carries the prefix argument, so the spec declares only the region and the prompts; a region command called without a region gets point to mark, and fails with no mark; errors from the call or the handler go to the echo area.)
- **Keymap layering**, highest priority first: transient map → minor-mode maps of the current buffer → major-mode map → global map. (Decided in [#21](https://github.com/Root-man/aiditor/issues/21): each layer is asked for the whole pending key sequence and the first that binds it, as a command or a prefix, wins, so a mode's `C-x a` does not hide the global `C-x C-s`; mode keymaps live in the core by mode name and each buffer names its major mode and minor modes; an unbound sequence shows `<keys> is undefined`, except that an unbound plain key still types or moves; `C-g` cancels a pending prefix.)
- **Key sequences** resolve through a trie, so prefix keys (`C-x`, `C-c`, `C-x 4`) work naturally, with a which-key style hint after a short delay. (Decided in [#25](https://github.com/Root-man/aiditor/issues/25): the hint shows after 1 s with a prefix pending and hides on the next key; it lists every key that can follow, sorted, with the command each runs under keymap layering or `+prefix`; it belongs to the frame's echo area, not to a window's display. The delay is not a setting yet.)
- **Prefix argument** (`C-u`, `M-<digit>`) is passed to every command. (Decided in [#23](https://github.com/Root-man/aiditor/issues/23): `C-u`, `M-<digit>` and `C--` are the commands `universal-argument`, `digit-argument` and `negative-argument`, following Emacs's rules, with digits and `-` read through the transient map; a command gets the raw form (`C-u`s without digits, a lone minus, or a number) with its value, so `C-u` and `C-u 4` differ; these commands keep the last command.)
- **Motion** (decided in [#27](https://github.com/Root-man/aiditor/issues/27)): the motion keys run Emacs's commands by Emacs's names (`forward-char`, `next-line`, `forward-word`, `move-beginning-of-line`, `beginning-of-buffer`, `scroll-up-command`, `recenter-top-bottom` and their partners), and the arrow keys are bound to the char and line commands. A motion that runs into an end of the buffer moves as far as it can and reports `Beginning of buffer` or `End of buffer`. The goal column of `C-n`/`C-p` is in chars until the display renders tabs and wide chars; in a wrapping buffer they move by visual rows (see Long lines). `M-<` and `M->` push the mark, as decided in #29. Scrolling uses the line count of the window's last redisplay.
- **Insertion and deletion** (decided in [#28](https://github.com/Root-man/aiditor/issues/28)): typing and the editing keys run Emacs's commands by Emacs's names (`self-insert-command`, `newline`, `electric-newline-and-maybe-indent` on `C-j`, `open-line`, `delete-char`, `delete-backward-char`, `kill-word`, `backward-kill-word`), repeated by the prefix argument, so `C-u 3 a` types `aaa`. Self-insert is what an unbound plain char runs, since a keymap can't bind every char. A negative count reverses the deletes and is an error for the inserts, and a delete that would pass an end of the buffer deletes nothing and reports it. Without a prefix, `DEL` and `C-d` delete an active, non-empty region instead, without saving it to the kill ring (Emacs's `delete-active-region`). `C-j` does not indent yet, and the kill commands save to the kill ring (#31).
- **Mark and region** (decided in [#29](https://github.com/Root-man/aiditor/issues/29)): Emacs's transient-mark-mode. The mark is active or inactive and only an active one shows the region; region commands still use an inactive mark. `C-SPC` (`set-mark-command`) pushes the old mark onto the window's mark ring of 16, sets the mark at point and activates it; right after itself it toggles the region; `C-u C-SPC` jumps to the mark and rotates the ring. `C-x C-x` (`exchange-point-and-mark`) swaps and activates. `C-g` and any command that changes the buffer deactivate the mark. `M-<` and `M->` push the mark at the old point, inactive, unless the region is active or the prefix is a plain `C-u`. The ring belongs to the window and is dropped when it shows another buffer. macOS binds Ctrl+Space to switching input sources by default, so `C-SPC` needs that shortcut freed or another key bound in `keymap.toml`. Not yet: shift-selection, `C-@`, repeated `C-SPC` popping after `C-u C-SPC`, the global mark ring.
- **Kill ring and clipboard** (decided in [#30](https://github.com/Root-man/aiditor/issues/30)): one kill ring of 60 entries, shared with the system clipboard as in Emacs. A kill also writes its text to the clipboard. A yank first pushes clipboard text the editor did not write itself onto the ring, so text copied in another app yanks with `C-y`, and that text is also saved to the ring before a kill overwrites the clipboard. `s-c`, `s-x` and `s-v` run `kill-ring-save`, `kill-region` and `yank` on macOS; on Linux, where KDE and GNOME take Super keys, `C-S-c`, `C-S-x` and `C-S-v` do, as in Linux terminals (moved in [#233](https://github.com/Root-man/aiditor/issues/233); these keys live in `keymap-macos.toml` and `keymap-linux.toml`, bound after `keymap.toml`). Plain text only, and no Linux PRIMARY selection. The core stays free of GPUI: a kill returns the clipboard write as an effect, and the frontend passes the clipboard's current text in with every kill and yank. (Built in [#31](https://github.com/Root-man/aiditor/issues/31): `C-k` `kill-line`, `C-w` `kill-region`, `M-w` `kill-ring-save`, `C-y` `yank` and `M-y` `yank-pop` follow Emacs, prefix arguments included; every kill counts as `kill-region` for appending, so consecutive kills join one entry, in front when killing backward, and `M-w` right after a kill joins it too. A command declares in its spec that it reads the clipboard, and the frontend reads the clipboard only before a key that runs such a command (`Core::wants_clipboard`), since a read costs a round trip to the display server on Linux; clipboard text is foreign when it differs from what the editor last wrote or took in. `M-y` not after a yank is an error, since there is no minibuffer for `yank-from-kill-ring` yet.)
- **Mouse**: none. The editor is keyboard-only; the frontend ignores clicks and the wheel, in text buffers and terminals alike. (Decided after [#238](https://github.com/Root-man/aiditor/issues/238), which removed click-to-move-point and wheel scrolling built in #12 under [#30](https://github.com/Root-man/aiditor/issues/30)'s decision.)
- **Windows** (built in [#35](https://github.com/Root-man/aiditor/issues/35)): the frame's windows form a binary split tree, each split stacked or side by side with a ratio, 0.5 when made. `C-x 2` and `C-x 3` split the selected window, the new one below or right showing the same buffer with the same point and first line but no mark; `C-x o` selects the next window top to bottom, left to right, a count moving that many, backward when negative; `C-x 0` gives the window's space to its sibling and selects the sibling's first window; `C-x 1` keeps only the selected one. Commands act on the selected window. The core lays the windows out in pixels for the frame size and cell width the frontend reports on resize (`Msg::Resize`, `Core::frame`), split edges snapped to whole lines and cells. The frontend ([#11](https://github.com/Root-man/aiditor/issues/11)) draws every window from that frame display. Not yet: resizing or balancing windows, `C-x 4` commands other than `C-x 4 b`.
- **Buffers** (built in [#42](https://github.com/Root-man/aiditor/issues/42)): `C-x b` (`switch-to-buffer`) completes over the buffers, the other ones most recently shown first and the current one last, so `RET` alone goes back to the previous buffer; a name no buffer has makes an empty buffer. `C-x 4 b` does the same in the next window, splitting below when there is one window, and selects it. `C-x k` (`kill-buffer`) lists the current buffer first; a modified buffer visiting a file asks `Buffer modified; kill anyway? ` over `no` and `yes`, `RET` alone declining. Windows showing a killed buffer show the most recent one left; `*scratch*` and `*Messages*` can't be killed ([#62](https://github.com/Root-man/aiditor/issues/62)). Each buffer keeps the point of the last window that stopped showing it, and a window showing it again starts there; there is no per-window buffer history yet. Names starting with a space are hidden from the lists, and a name already taken gets `<2>`, `<3>`. Visiting and switching make a buffer the most recent; selecting a window does not. `C-x b` previews the selected buffer in the selected window ([#69](https://github.com/Root-man/aiditor/issues/69), see Minibuffer); `C-x 4 b` and `C-x k` don't.
- **Messages** (built in [#47](https://github.com/Root-man/aiditor/issues/47)): every echo-area message, and every `tracing` warning and error in the format stderr gets (without colour), is appended as a line to a read-only `*Messages*` buffer, without undo. It is made on the first line, so it is missing from the buffer list until something is logged, and can't be killed ([#62](https://github.com/Root-man/aiditor/issues/62)). There is one for the app, owned by no workspace (decided in [#61](https://github.com/Root-man/aiditor/issues/61), see Workspaces). Not yet: point following new lines, a size cap; a log line is dropped while the services channel is full.
- **Find file** (built in [#41](https://github.com/Root-man/aiditor/issues/41)): `C-x C-f` (`find-file`) prompts `Find file: ` with the text starting as the current buffer's directory, its file's, a terminal's cwd, or else the working directory, with a trailing `/`. The list holds the entries of the directory typed up to the last `/`, sorted by name, subdirectories (symlinks followed) ending in `/`, fuzzy-matched against the text after it; the file service lists the directory on Tokio's blocking pool and the list fills when the listing arrives, a listing for a directory the text has left being dropped. `TAB` puts the directory plus the selected entry in the text, and `RET` on a selected directory enters it the same way (Vertico's `vertico-directory-enter`); `M-RET` (`minibuffer-exit-input`, Vertico's `vertico-exit-input`) returns the text as typed in any completing minibuffer, which is how to name a new file that fuzzy-matches an existing one. A relative answer is taken from the buffer's directory. A path a buffer already visits switches to it without reading the file; otherwise the file service reads it, a missing file gives an empty buffer visiting it, and a binary or non-UTF-8 file is refused with `<path>: <reason>` and no buffer, as File handling says. Command-driven reads carry their originating workspace, window and request identity. Switching workspace or window, deleting the origin, switching buffers, starting another visit or opening another prompt permanently abandons the pending visit, even if focus returns. Its late result or error changes nothing; ordinary edits do not cancel it. Deferred grep positions belong to that same request. Startup file loading keeps its existing behavior. Paths are compared as given, so `..` or a symlink to a visited file makes a second buffer. `DEL` (`minibuffer-directory-delete-char`, Vertico's `vertico-directory-delete-char`) with point at the end of a text that ends in `/`, or whose last component is a directory in the listing already loaded (no new IO), deletes back to just after the previous `/`, so `~/a/b/` and `~/a/b` both become `~/a/`; it deletes one char otherwise, with a prefix argument or an active mark, and in other completing prompts. Not yet: `~` and environment variables, Emacs's `//` and `~/` resets, dired, `find-file-other-window`, a directory per buffer apart from its file's.
- **File index** (built in [#68](https://github.com/Root-man/aiditor/issues/68)): each project's files, per root and relative to it, sorted, kept in memory only and rebuilt on demand, so the finder across roots ([#70](https://github.com/Root-man/aiditor/issues/70)) never walks while the user types. `project-index` (`C-x p i`) prompts `Project: `, echoes `Indexing <project>...`, and the file service walks every root on Tokio's blocking pool with the `ignore` crate: `.gitignore` applies in or out of a git repo, as do `.ignore` and git's global excludes; hidden files are in, `.git` never is, and symlinked directories are not followed. The answer replaces the index and echoes `Indexed <n> files in <project>` (`file` for one), each root that couldn't be read named after it; an answer from an older walk, or for a project no longer loaded, is dropped. One walk runs per project, with one latest queued refresh holding the newest roots and ignore patterns. Superseded results start that queued walk without replacing the accepted snapshot. An explicit completion announcement survives quiet refresh requests and appears once for the final accepted result. Same-scope refreshes retain accepted counts, root-watch eligibility and mode lines; changed scopes wait for fresh successful counts, while partial-root results retain their available files and error reporting. fzf was ruled out: it only matches, is an external binary, and can't drive the minibuffer, which already matches with `nucleo`. Creates, deletes and lost events refresh watched projects quietly (#80, #191); unwatched projects refresh on demand. Not yet: a parallel walk.
- **Find file across roots** (built in [#70](https://github.com/Root-man/aiditor/issues/70)): `project-find-file` (`C-x p f`, Emacs's key) prompts `Find file in <project>: ` for the current workspace's project and matches with `nucleo` over every indexed file as `<root name>/<path relative to the root>`, the primary's files first. A root's name is its directory's last component, `<2>`, `<3>` for one an earlier root of the project already has. `RET` visits the selected file as `find-file` does; text matching nothing, or returned with `M-RET`, is visited under the root its first component names, else under the primary, so it can make a new file. A project with no index yet is indexed when the finder opens. The finder captures roots and their unique labels from the displayed snapshot, or from the initial pending scope, so typed root prefixes work before the walk finishes. Preview, selection and typed acceptance keep this mapping until the prompt closes. Only an initial result with compatible roots can fill a waiting prompt; a displayed snapshot stays fixed. A reopened finder uses the latest compatible snapshot or waits for one after a scope change. The finder asks its own question so it can start that walk first, so it keeps no `M-p` history. The finder and `C-x C-f` preview the selected file (see Minibuffer); a selected directory shows nothing.
- **Minibuffer** is a real one-line buffer with its own keymap, history rings and a vertical fuzzy completion list. It hosts the consult-style commands (buffers, files across project roots, project grep, `M-x`) with live preview, and the swiper-style in-buffer search. (Built in [#38](https://github.com/Root-man/aiditor/issues/38): a command called with fewer strings than its prompts opens the minibuffer instead of failing, a fresh buffer in major mode `minibuffer-mode` in its own window, selected while open, with the prompt drawn before its text in the echo area line rather than kept in the buffer; `RET` (`exit-minibuffer`) calls the command again with the text as the next string and the prefix argument it was first given, so prompts chain, and `C-g` (`abort-minibuffers`) closes it with `Quit`; other keys fall through to the global keymap. Each prompt text has its own history of 100, newest first, skipping empty answers and repeats of the newest; `M-p` and `M-n` (`previous-history-element`, `next-history-element`) step through it with Emacs's messages at the ends, and stepping back past the newest restores what was typed. Not yet: recursive minibuffers, which fail; leaving the minibuffer open for another window, so `C-x 2`, `C-x 3`, `C-x o`, `C-x 0` and `C-x 1` fail in it; IME marked text drawn at a prompt. Built in [#39](https://github.com/Root-man/aiditor/issues/39): a command's spec can give candidates for its prompts, and its minibuffer then lists the ones that fuzzy-match the text with `nucleo`, best first and all in the given order for empty text, 10 rows below the prompt line, the selected one highlighted and kept in view; `C-n` and `C-p` (`minibuffer-next-completion`, `minibuffer-previous-completion`, also the arrows) move the selection and stop at the ends, `TAB` (`minibuffer-complete`) puts the selected candidate in the text, `RET` returns the selected candidate, or the text when nothing matches, and changing the text selects the first match again. These keys are the `minibuffer-completion` keymap, a minor mode of completing minibuffers only. `nucleo` matches on its own threads; the core polls it after each message, waiting up to 10 ms, and on each frame, and polls again on a 16 ms timer while it is still matching. A command's own further question (a confirmation such as `Save file <path>? `) passes its choices in place of the spec's candidates, and its answers keep no history, as Emacs's `y-or-n-p`. A match count before the prompt, vertico's `1/100 M-x `, came with #54. Not yet: highlighting matched chars, cycling (returning the text while something matches came with #41). Built in [#160](https://github.com/Root-man/aiditor/issues/160): the list only grows while one minibuffer is open, as Emacs's `resize-mini-windows` = `grow-only` and Vertico's default: it keeps the most rows it has shown, the rest drawn empty, so the windows above never jump as matches come and go, and the next minibuffer starts at the rows its own matches need. Built in [#40](https://github.com/Root-man/aiditor/issues/40): `M-x` (`execute-extended-command`) completes at the prompt `M-x ` over every registered command in name order and runs the chosen one with the prefix argument `M-x` got, as that key sequence's command. A command's spec can annotate its candidates; annotations are worked out as the minibuffer opens, drawn dimmed after each candidate and never matched. `M-x` annotates each command with the shortest key that runs it under keymap layering in the buffer it was called from, the first in `kbd` order among equally short ones. Not yet: `C-u M-x` shown in the prompt, Emacs's "You can run the command with" hint, recently used commands first. Built in [#69](https://github.com/Root-man/aiditor/issues/69): a command's spec can preview, naming the buffer to show for a candidate; while its minibuffer is open, the window it was opened from shows the selected candidate's buffer from the moment the list opens, following every change of the selection, and shows itself as it was when the hook names no buffer. The original window is set aside whole while a preview stands in for it, so every way the minibuffer closes (`C-g`, `RET`, a workspace switch) puts it back exactly as it was, point, mark, mark ring and scroll included; `RET` then runs the command from it. Previewing never makes a buffer the most recent. Preview reads are coalesced across prompt sessions: one active worker and one latest pending selection. Closing a prompt cancels its queued request and makes its active result obsolete. Validation, decoding and Rope preparation run on the worker without an unused content hash; only the matching session/request can install prepared text. Built in [#70](https://github.com/Root-man/aiditor/issues/70): a preview can name a file instead of a buffer. A file visited in the current workspace shows its buffer; any other is read by the file service into one hidden, read-only preview buffer that visits it, the window keeping what it showed until the read answers, and an answer for a file no longer selected is dropped. That buffer is killed when the next file is read and when the minibuffer closes, so `RET` visits the file afresh, as consult does without keeping it. A missing, binary or unreadable file shows the window as it was. A command that declares no prompts previews its own question, as `project-find-file` does. Not yet: a size limit on previewed files, so a huge file is read whole. Built in [#75](https://github.com/Root-man/aiditor/issues/75), for swiper: a command can filter its candidates itself in place of `nucleo`. Its matches keep the order it gives. When the text changes, the selection stays on the selected candidate if it still matches, else moves to the next match after it, else to the last, and `RET` with no match says `Match required`. A command can preselect a candidate. A preview can name a position in the original window's buffer. A copy of the window stands in, keeping its scroll from one such preview to the next and centering point's line only when it is out of view. A filtering prompt's history keeps the typed text, from `RET` and `C-g` alike. Each minibuffer has its command's name as a minor mode, so a keymap named after the command binds keys at its prompts, as ivy's `:keymap`.)
- **Swiper** (built in [#75](https://github.com/Root-man/aiditor/issues/75), replicating ivy's `swiper`): `C-s` prompts `Swiper: ` over every line of the buffer.
  - **Listing:** lines appear in buffer order after their line numbers, which are not matched, with the line at point selected. The prompt flattens a buffer snapshot once into a string with line byte ranges and formats labels only at the completion boundary; it shares one compiled query revision across filtering, preview and acceptance. Preview and acceptance positions follow the live origin buffer if it changes.
  - **Matching:** words separated by spaces must appear in order (`ivy--regex-plus`). Each word is a regexp in the Rust `regex` syntax, matched literally when invalid; `\ ` is a space, and words after `!` exclude lines. Matching ignores case while the input has no upper-case letter.
  - **Preview:** the window shows point at the end of the first match on the selected line.
  - **`RET`:** goes there. When point moved and no region is active, it saves the mark where the search started (`Mark saved where search started`).
  - **`C-s` at the prompt:** selects the next match, or with empty input recalls the last search.
  - **Performance limit:** each query still scans every line on the core thread, with one flat text copy and line ranges retained for the prompt. The verification follow-up's 100,000-line debug fixture opens in 4.053 ms and has query medians of 4.111–11.369 ms; it replaces the slower direct Rope scan. These are core timings, not GUI latency guarantees; no background filtering, global cache or size cutoff is present. Reproduction and fixture details are in the M1 refactor validation notes.
  - **Not yet:** highlighting the matches and the line, which needs text properties that can be removed or scoped to a window; swiper's `M-q`, `C-l`, avy, multiple cursors, face matching and occur.
- **Kill ring, mark ring, registers and keyboard macros** belong in the core, because they depend on the command loop.
- **Undo** is linear with a redo stack, per buffer, and grouped per command. An auto-revert from disk is one undo group, so an agent's edit to an open file can be undone in one step. (Decided in [#16](https://github.com/Root-man/aiditor/issues/16): redo is a separate stack, not Emacs's undo-of-undo, and a new edit clears it; up to 20 consecutive typed characters share a group; undo puts point where it was before the command, redo where it was after. Undo is `C-/`, `C-_` and `C-x u`, redo is `C-?`.)
- **Editing commands** (decided in [#72](https://github.com/Root-man/aiditor/issues/72)): `C-s` runs swiper ([#75](https://github.com/Root-man/aiditor/issues/75)); there is no isearch, and `C-r` is unbound. The rest come in M5's editing epic ([#118](https://github.com/Root-man/aiditor/issues/118)):
  - `M-;` (`comment-line`) toggles comments on the current line, or on every line of the active region, with the comment markers of the buffer's major mode. Not Emacs's `comment-dwim`.
  - `M-q` (`fill-paragraph`) refills the paragraph around point, the lines between blank lines, at column 80 until settings are decided. In Markdown it keeps a list or quote prefix (`- `, `1. `, `> `) and leaves headings, tables and fenced code alone.
  - `M-%` (`query-replace`) asks at each literal match, answering `y`, `n`, `!` (replace the rest) and `q`. There is no regex variant; replacing across files is left to editable grep results and agents.
  - `C-x C-w` (`write-file`) asks for a path with the find-file prompt, makes the buffer visit it and renames the buffer, asking before overwriting a file and refusing a path another buffer visits; `C-x C-s` in a buffer with no file asks the same way. Until then a buffer with no file can't be saved.
  - Recent files: one global list of the 100 most recently visited files in the app's state directory, opened with `recentf-open` and shown by the welcome dashboard ([#193](https://github.com/Root-man/aiditor/issues/193)).
- **Indentation.** TAB indents the current line for the buffer's language. How the indentation rules are defined is to be decided (tree-sitter indent queries, as Helix uses, are one option).
- **Formatters** run as a command, configured per language in TOML (`mix format`, `rustfmt`, prettier), with the project's process environment. They do not run on save in the MVP.
- **Prefixes.** One prefix for workspace commands and one for agent commands (new session, send region or buffer, switch session, cycle mode, cancel turn).
- **Keys from the frontend** (decided in [#9](https://github.com/Root-man/aiditor/issues/9), from the [GPUI spike](spikes/gpui.md)). GPUI's own keymap stays empty, and the editor view's `on_key_down` sorts keys into two streams:
  - *Commands.* A key with Ctrl, Cmd or Fn held, with Option held in Meta mode, one that types nothing, or RET, TAB, DEL or ESC is consumed and sent to the key trie as `Msg::Key`. Cmd is the `s-` (super) modifier; the global keymap binds `s-c`, `s-v`, `s-x`, `s-z`, `s-s`, `s-q`, `s-w` and `s-h` by default (`s-c`, `s-x` and `s-v` are copy, cut and paste through the kill ring, as decided in #30; on Linux they are `C-S-c`, `C-S-x` and `C-S-v` instead, since #233). (Built in #12: `s-z` and `s-s` are bound; `s-c`, `s-x` and `s-v` came with the kill ring in #31, and `s-q` with quitting in #48, bound like `C-x C-c`; `s-w` and `s-h` stay unbound until frames exist. Keys with Fn held, F-keys, Home, End, PageUp, PageDown and forward Delete are dropped until a binding needs them.)
  - *Typing.* Every other key propagates to the platform's text input, so dead keys and IMEs work. Text arrives through GPUI's input handler as `Msg::Insert { text, replace }`; `replace` is an optional range (in UTF-16 units, converted by the core) for input methods that rewrite text already typed, such as macOS press-and-hold, and that rewrite is a normal undoable edit. Self-insert, keyboard macros and the test harness all handle `Insert`; in key scripts, plain characters are `Insert`s. (Built in #12: the core feeds each inserted char through the key path as a plain key, so a pending prefix, the prefix argument and keymaps see typed chars as they see keys.)
  - *Option on macOS.* One setting: Option as Meta (default) or Option for characters and dead keys. Left and right Option cannot be told apart. On Linux, Alt is always Meta. The setting is `option_as_meta` (default `true`).
  - *IME marked text* is a preedit overlay in the window's display state, never in the rope, so it stays out of undo, auto-save and macros. (Built in [#12](https://github.com/Root-man/aiditor/issues/12) and [#11](https://github.com/Root-man/aiditor/issues/11): the frontend holds the marked text, as platform input state, and lays it out underlined inside point's line with the cursor after it; committing or unmarking it sends it as an `Insert`.)
  - *Non-Latin layouts.* A modified key resolves by the character it types, so `C-ч` is just unbound, as in Emacs.
- **Multiple cursors** come after the MVP. When they land, they are part of the window's selection state, editing commands run once per cursor, and the whole run is one undo group.

Keymaps and all other settings live in TOML files, reloadable at runtime. Runtime reads and filesystem validation run in one background request for settings, keymaps and projects, leaving typing responsive. Accepted bundles apply in that order with independent component fallback. A successful runtime reload (`C-x C-r` or `M-x reload-settings`) shows `Configuration reloaded` in the echo area and logs it to `*Messages*`; any read, parse, validation or binding diagnostic stays visible instead. Only an accepted bundle announces completion, after application, without waiting for background indexing or watching. The message follows the normal next-key lifetime; startup does not announce a runtime reload. One active and one latest pending request discard obsolete bundles; a project edit completed after a snapshot started forces a fresh project snapshot. Startup may read synchronously before a window exists. There is no scripting language. (Decided in [#24](https://github.com/Root-man/aiditor/issues/24): keymaps live in their own `keymap.toml`, bundled and in the config dir beside `settings.toml`, with one table per keymap (`[global]` or a mode name) mapping `kbd` sequences to command names; the user file is bound over the bundled one entry by entry; unlike settings, a bad entry (bad keys, unknown command, a value that is not a name) is skipped and reported while the rest loads, and only a file that is unreadable or not TOML keeps the keymaps in effect; `C-x C-r` reloads both files. Unbinding a default key is not supported yet.)

## ACP integration and session management

The editor is an ACP **client**. Each agent session spawns its own agent process (Claude Code through `claude-agent-acp`, Codex through `codex-acp`), talks JSON-RPC over stdio, and lives in the workspace it was created in; after that workspace is killed, the session can be resumed in another workspace of the same project.

**Project scope, the same way the CLIs and desktop apps do it.** The editor does not run an MCP server. Since June 2026 ACP has a stable way to pass extra roots: `session/new` takes `cwd` as the primary working directory and `additionalDirectories` as further absolute paths, which the agent treats as part of its filesystem scope. The client may only send them when the agent advertises `sessionCapabilities.additionalDirectories` ([ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup)); both the Claude Code and Codex adapters do (checked).

- `cwd` = the project's primary repo. The agent loads its own config from there: AGENTS.md or CLAUDE.md, MCP servers, settings. The editor passes no MCP servers of its own.
- `additionalDirectories` = every other repo and folder in the project.
- The first prompt of a session carries a short preamble: the list of roots with their role lines from the project file.
- Nothing else is attached to prompts automatically. Context goes in only through explicit commands such as sending the region or the buffer.

**Agents use the disk, not the editor's buffers.** The editor does not advertise the ACP `fs.readTextFile` or `fs.writeTextFile` client capabilities. Agents read and write files with their own tools, so the agent, its shell commands and `git diff` all see the same files. The file watcher catches every change and auto-reverts the open buffers visiting those files; a buffer with unsaved edits goes into the conflict flow instead.

**Components**

- **Agent registry.** Claude Code (claude-agent-acp) and Codex (the maintained @agentclientprotocol/codex-acp) in TOML: command, args, env, and a default mode per agent. Processes start with the environment described under Process environment. (Decided in [#278](https://github.com/Root-man/aiditor/issues/278): `[agents.<name>]` tables in `settings.toml` with `command`, optional `args`, `env` and `default_mode`, merged over the bundled settings key by key, so a user table changes one key of a bundled agent or adds an agent. The bundled settings define only `claude`, running `claude-agent-acp` from `PATH` in `auto` with `CLAUDE_CODE_ENABLE_TASKS` and `CLAUDE_CODE_ENABLE_TODO_TOOLS` set, since the Claude Agent SDK leaves the tools that send ACP plans off (found testing [#295](https://github.com/Root-man/aiditor/issues/295)); Codex is one user table away. An unknown key, a wrong type, an empty command or a bad `env` variable rejects the settings file like any other settings error. `default_mode` is not checked until the agent advertises its modes; since [#305](https://github.com/Root-man/aiditor/issues/305) an unknown one is noted when the session opens. `project-set-default-agent` completes over the registry and refuses other names.)
- **One process per session.** A crash ends only that session; the agent's stderr goes to a log buffer. (Built in [#280](https://github.com/Root-man/aiditor/issues/280): `agent-start` (M-x only, like `vterm`) asks `Agent: ` over the registry with the project's `default_agent` preselected and starts it in the current workspace's project: `cwd` is the primary repo, the environment the captured one, then the registry's `env`, then the project file's. While the project's environment is being captured the spawn waits for the answer. Each session gets a read-only `*<agent> stderr*<<workspace>>` buffer owned by the workspace, not shown; since [#292](https://github.com/Root-man/aiditor/issues/292) the session buffer is the session's handle instead, so killing it (asked first, like a live terminal) or its workspace stops the agent, killing the log buffer only drops later stderr, and quitting asks `Active processes exist; ...` while a session is live. `*Messages*` notes `<agent> session ready (modes: ...)` (also echoed, replacing `Starting <agent>...`), a failed start (also echoed), and an exit the editor didn't cause; the log buffer stays after the exit. `session/update` notifications are kept per session, unrendered. Agent requests are still refused. Since [#305](https://github.com/Root-man/aiditor/issues/305) the modes in the ready note are the values of the session's mode option (see Modes and auto-approve), and if `default_mode` is one of them and not the current value the core sends `session/set_config_option`; an unknown `default_mode` notes `<agent> has no mode <value>` and a refused set `<agent> could not set mode <value>: <reason>` in `*Messages*`, leaving the mode alone.))
- **Threading (decided in [#95](https://github.com/Root-man/aiditor/issues/95)).** The ACP client is a service on the existing Tokio runtime, like the PTY and file services; no single-threaded executor or dedicated thread. `agent-client-protocol` 3.x is `Send` throughout: request and notification handlers, connection handles and the `connect_with` future must all be `Send + 'static`, and the crate depends on no runtime (it drives its own tasks inside that future with `futures`). A throwaway client and fake agent on `Channel::duplex`, each in a `tokio::spawn` on a multi-thread runtime, initialized and streamed a `session/update` with the handler running on a Tokio worker (3.5.0, the version Zed pins). Handlers only forward each request (with its responder) and notification onto the service channel; the core decides and the service sends the reply, so no core state crosses threads. Zed does the same: the connection future runs on GPUI's background executor and its handlers enqueue onto a foreground dispatch queue. The crate's optional `process` feature spawns agents with `async-process`, which brings its own reactor thread; spawning with `tokio::process` and wrapping its pipes with `tokio-util`'s compat layer into `ByteStreams` avoids that, at the cost of killing the agent's process group ourselves, which `process` does for `npx`-style wrappers. Decided in [#279](https://github.com/Root-man/aiditor/issues/279): `tokio::process` with the compat layer; each agent leads its own process group, which a kill or quit sends SIGTERM and, 100 ms later, SIGKILL, as with terminals.
- **Session manager.** Keeps an index of sessions: ACP session id, agent, project, `cwd` and additional directories, title, last activity, status. It stores no transcript. The index is the only state that survives a restart. A resume command lists the project's past sessions and continues the chosen one in the current workspace with `session/load`, which replays the history into the session buffer; `session/resume` does not replay history, so it isn't used. Both adapters support loading across processes ([ConnectOnion's adapter matrix](https://docs.connectonion.com/useful-tools/acp-agent)). If the agent can list its own sessions, the resume list also shows sessions started outside the editor, such as in the Claude Code CLI; adapter support is to be checked.
- **Session buffer.** A rich chat view like the Claude Code and Codex apps: rendered markdown, collapsible tool calls, the agent's plan, the current mode, and a multi-line prompt area at the bottom with Emacs editing. Swiper search, mark and kill, and copying all work with Emacs keys.
  - **Display model (decided in [#8](https://github.com/Root-man/aiditor/issues/8)).** The session buffer is a rope like any other buffer. The structured transcript is the source of truth; the core renders it into the rope as markdown text with properties: faces, `read-only`, `invisible` (hidden markup and folded tool calls) and line decorations (code-block background, a rule beside tool calls). The markup stays in the text and is only hidden, so search matches it and kill or copy yield markdown. Permission prompts are text with key-bound buttons; plan entries are plain text for now, buttons after the MVP.
  - **One buffer, as in comint.** Everything before the prompt marker is read-only; streamed output is inserted above it, and only the message being streamed is re-rendered, at most once per frame. `RET` in the prompt area sends the input and `C-j` (or `S-RET`) inserts a newline, as in comint. The text projection is the buffer itself, so search, mark and kill need nothing extra. (Built in [#292](https://github.com/Root-man/aiditor/issues/292): `agent-start` creates and shows `*<agent>*<<workspace>>` in `agent-session-mode`, its text the prompt line `> ` with point after it. The prompt area runs from after `> ` to the end; an edit inserting before it or deleting any text before it is refused with `Text is read-only`, and output goes in above the prompt line without undo, the prompt area keeping its text and undo. Each block above the prompt (an echoed input, a reply, a turn-end line) ends with a blank line. `RET` (`agent-send-input`) sends the prompt area's text, from anywhere in the buffer, as one text block in a `session/prompt`; the text stays above as the echo (`> hello`, like a frozen prompt), a new `> ` line starts below it with point there, and the buffer's undo is cleared. Empty or whitespace-only input sends nothing. `RET` echoes `<agent> is not ready` before `session/new` is answered, `<agent> is busy` while a turn runs and `<agent> session has ended` after an exit, sending nothing. `S-RET` is `newline` in the mode and `C-j` the global newline. `C-c C-c` (`agent-cancel`) sends `session/cancel` while a turn runs, else echoes `No turn is running`. Text agent message chunks are appended as they stream, consecutive chunks joining into one block; the `session/prompt` answer ends the turn, adding `Turn ended: <reason>` for a stop reason other than `end_turn` (`max_tokens`, `max_turn_requests`, `refusal`, `cancelled`) or `Error: <message>` for an error answer. The service answers prompts after the turn's updates, as its response callback runs before the next message is dispatched. Other updates are kept and unrendered (tool calls are shown since #294, the plan and mode since #295). Each chunk edits the rope at once. Not yet: input history.) (Markdown built in [#293](https://github.com/Root-man/aiditor/issues/293): agent messages, thoughts and the echoed prompt's text are parsed with `tree-sitter-md` and rendered as properties: ATX and setext headings bold in `text.title`, emphasis italic, strong bold, inline code in `text.literal` on the theme's `code_block`, link text and autolinks underlined in `text.uri`; heading markers, delimiters, backticks and a link's brackets and destination are invisible with no placeholder. Every line of a fenced or indented code block gets a `code_block` background, and a fence line's text is hidden, its newline kept, so it shows as an empty line of the block. Thought chunks are now blocks of their own in the theme's `dim` colour; a message chunk after a thought, or the other way round, starts a new block. The streamed block's text goes in per chunk, but its properties are re-rendered when the frontend builds the frame (`Core::frame`), once however many chunks came; a block renders at once when the next one starts, and the echo when it is sent. `Turn ended` and `Error` lines stay plain. Lists, quotes, tables and code highlighting are shown as text. With folds, the display looks up only the properties near the window, widened by the newlines folds hide, and `properties_near` bisects while property starts and ends both ascend, which the renderer's output keeps.) (Tool calls built in [#294](https://github.com/Root-man/aiditor/issues/294): each `tool_call` adds a block, a header line `<title> (<kind>, <status>)` (the title's first line as markdown, ` …` if it has more, the ACP names of kind and status in `dim`, a `dim` rule beside it) and, under it, its content folded: invisible, shown as ` …`. The content is everything the agent sent, uncut: `Input:` with the whole `rawInput` as pretty JSON, each content item (text as markdown, a resource link's URI, a diff as its path and a unified diff, `Terminal <id>`, `[<type>]` for the rest), and `Output:` with the whole `rawOutput` when no content item carries the result, which is how Claude's adapter sends one or the other; fences outgrow the backticks they enclose. `tool_call_update` merges into the call and rewrites its block where it is, by changed lines, keeping its fold; an update for an unknown id starts a block if it has a title. `TAB` (`agent-toggle-tool-call`) on a header shows or hides the content, rendered as markdown with the rule beside each line; inside open content it hides it and moves point to the header, as in magit; elsewhere it echoes `No tool call here`. A folded block's properties never nest, and `add_property` inserts at the sorted place while the order holds, so rewriting a block mid-transcript keeps `properties_near` bisecting. `C-n`, `C-p` and scrolling treat a line starting inside invisible text as part of the fold's first line, as Emacs's `line-move-ignore-invisible`; other motion and search can still land inside a fold.) (Plan and mode built in [#295](https://github.com/Root-man/aiditor/issues/295): the first `plan` update adds a block, `Plan` then a line per entry, `<content> (<status>, <priority>)` with the content's first line (` …` if it has more) and the ACP names in `dim`, a `dim` rule beside every line; each later `plan` replaces the entries in that block where it is, as tool call updates do, and an empty plan leaves `Plan` alone. The session buffer's mode line shows ` [<mode>]` after the name, the mode option's current value from `session/new`, following each `config_option_update` and `session/set_config_option` answer (since [#305](https://github.com/Root-man/aiditor/issues/305)).) (Mode cycling built in [#306](https://github.com/Root-man/aiditor/issues/306): `S-TAB` (`agent-cycle-mode`), as in Claude Code, sends `session/set_config_option` setting the mode option to the value after its current one in the option's order, groups flattened, wrapping around; the mode line follows the answer, with no echo. The values and current value are the latest reported by `session/new`, `config_option_update` or a set answer, so a change the agent makes itself is where the next cycle starts. It works while a turn runs. It echoes `<agent> has no modes` without a mode option, and `<agent> is not ready` or `<agent> session has ended` as `RET` does, sending nothing; a refused set notes `<agent> could not set mode <value>: <reason>` with the value sent. Two presses before the answer send the same value.)
  - **Monospace in the MVP.** After the MVP, block rows (non-text rows between lines that point skips) and faces with their own font and size bring it up to Zed's agent panel: proportional prose, larger headings, cards for permissions and diffs.
- **Status.** Expect two or three concurrent sessions. Mode-line status, a dashboard and notifications come after the MVP.
- **After the MVP:** `@file` mentions, slash commands (`available_commands_update`), image paste, and rendering the diffs that tool calls include.

**Modes and auto-approve.** Both agents expose their approval levels over ACP as session modes. The Claude adapter advertises `auto`, `default`, `acceptEdits`, `plan`, `dontAsk` and `bypassPermissions` ([block/buzz#2885](https://github.com/block/buzz/pull/2885)), with `bypassPermissions` offered only when bypass is enabled in the adapter. The maintained Codex adapter uses `read-only`, `agent` and `agent-full-access`, and can start in a chosen mode via `INITIAL_AGENT_MODE` ([openab#1353](https://github.com/openabdev/openab/pull/1353)); codex-acp 2.2 adds `workspace-write`, and `agent` there is "Auto review", where a reviewer model approves instead of the client (seen recording [#286](https://github.com/Root-man/aiditor/issues/286)). Claude Code starts in auto and Codex in agent, both set in config, and `S-TAB` cycles modes per session (built in [#306](https://github.com/Root-man/aiditor/issues/306)); any permission request that still arrives is answered inline in the session buffer.

**Config options over session modes (decided in [#305](https://github.com/Root-man/aiditor/issues/305)).** The editor reads the mode from ACP session config options, not session modes: the session's mode is the first option in `session/new`'s `configOptions` with category `mode` (a select), and an agent without one has no mode. ACP supersedes session modes with config options, both adapters send a `mode` option alongside their modes (seen in the recorded transcripts), and Codex's plan mode and model picking exist only as config options, so they become one more `configId` later instead of a second mechanism. The mode follows `config_option_update` and the answer to `session/set_config_option`, which carries every option; `current_mode_update` is ignored.

## Subsystems

**Terminal.** Built on `alacritty_terminal` for VT emulation and `portable-pty` for the PTY. The PTY service spawns off the UI thread with `TERM=xterm-256color`, `COLORTERM=truecolor`, `TERM_PROGRAM=aiditor` and `TERM_PROGRAM_VERSION` set to the editor version. It inherits the editor's environment with extra variables on top, defaults `LANG` to `en_US.UTF-8` when unset, removes `SHLVL`, and sets the PTY's `IUTF8` input flag on macOS and Linux for UTF-8 canonical-mode erase. The terminal variables override extra variables. (Input and resize built in [#215](https://github.com/Root-man/aiditor/issues/215): the PTY opens on the caller's thread, so a resize is one non-blocking ioctl there, and input is queued, in order, to a writer thread per terminal, so a paste into a program that isn't reading never blocks the UI. Input or a resize for an unknown terminal is ignored.) Kill ([#216](https://github.com/Root-man/aiditor/issues/216)) frees the terminal's PTY, writer and queued input at once and sends SIGHUP, then SIGTERM, to the shell's process group and the PTY's foreground process group, then SIGKILL after 100 ms; dropping the master alone wouldn't hang up the shell, since the reader holds a duplicate of it. Quitting kills every live terminal, blocking once for the 100 ms grace. Asking before killing a live terminal belongs to terminal buffers. A workspace usually holds several shells. Each terminal has two modes, as in vterm: *char mode* sends almost every key to the shell, *copy mode* turns the scrollback into a read-only buffer where Emacs motion, search and kill work. Shell-integration escape codes (OSC 133 prompt marks, OSC 7 cwd) give jump-to-prompt and per-command output capture. (Recording built in [#243](https://github.com/Root-man/aiditor/issues/243); copy mode's prompt jumps and output selection read the marks. alacritty drops both, so `Terminal::feed` also runs vte's low-level parser, which stops after each OSC 133, OSC 7, ED 3 and RIS; alacritty is fed that prefix and the event is applied against its grid. Marks `A`, `B`, `C` and `D` (with its exit code when given) keep the absolute line of the cursor, scrollback plus screen row; they are ignored on the alternate screen and dropped by ED 3 on the main screen or RIS. Once the scrollback holds its 10,000 lines alacritty stops counting dropped lines, so marks are dropped and not kept until it is cleared, and a column resize can shift marks below a rewrapped line. OSC 7's `file://` or `kitty-shell-cwd://` path, percent-decoded, becomes the terminal's cwd when the host is empty, `localhost` or this machine's `gethostname`; anything else is ignored, as program output is untrusted. Until then the cwd is the directory `vterm` spawned the shell in. A terminal buffer's directory is its cwd ([#244](https://github.com/Root-man/aiditor/issues/244)), so `C-x C-f` and `vterm` from it start where the shell is. The second parser costs about 3% on the 64 KB benchmarks: `yes` 0.64 ms, `cat` 0.63 ms.) zsh and starship send neither sequence, and Ghostty's integration only loads in shells Ghostty starts, so aiditor injects its own ([#247](https://github.com/Root-man/aiditor/issues/247)), as Ghostty does: when a terminal runs the default shell and it is zsh, the PTY service writes a `.zshenv` compiled into the binary to `shell/zsh` in the platform data dir and starts zsh with `ZDOTDIR` there, passing the user's `ZDOTDIR` in `AIDITOR_ZDOTDIR`. That `.zshenv` restores or unsets `ZDOTDIR` and sources the user's `.zshenv`, so zsh reads the user's other files and nested shells behave as outside aiditor. In interactive shells, the first prompt moves its precmd hook after the others, starship's included; it sends `133;D;<status>` when a command ran, `133;A` and `7` (`file://$HOST` and the percent-encoded `$PWD`) before each prompt and adds `133;B` to the end of `PS1` once, and a preexec hook sends `133;C`. A theme that rewrites `PS1` in its own hook gets no `B` on the first prompt; starship sets its prompt once. A failed write starts zsh without integration. Bash, fish and given commands start unchanged.

**Keys in char mode** (decided in [#89](https://github.com/Root-man/aiditor/issues/89)). `C-x`, `C-c` and `M-x` stay with the editor, as do Cmd keys, which never reach the shell; prefix sequences under `C-x` and `C-c` run through the keymaps as in any buffer. Every other key goes to the shell, `C-g` and `C-u` included. `C-c C-c` sends `^C`. There is no send-next-key command, so a raw `C-x` or `M-x` never reaches the program (readline's `C-x C-e`, zsh's `M-x`, nano's exit); add one if that is ever missed. An agent prefix under `C-c` or `C-x` therefore works in terminals too. (Built in [#232](https://github.com/Root-man/aiditor/issues/232): keys are encoded as xterm does, following Zed's `keys.rs`, with arrows, Home and End in the cursor mode the program set; `C-c C-c` is `vterm-send-C-c` in the `vterm-mode` keymap; text from the platform's input goes to the shell whole; a key xterm has no bytes for, like `C-1`, is dropped. Paste built in [#233](https://github.com/Root-man/aiditor/issues/233): the paste key, `s-v` on macOS and `C-S-v` on Linux, runs `vterm-yank`, so on Linux `C-S-v` stays with the editor too, while `C-v` still reaches the shell. `vterm-yank` sends the newest kill, clipboard text from another app first, to the shell; bracketed between `\x1b[200~` and `\x1b[201~` with every ESC removed when the program turned on mode 2004, as Zed does, else as is. `C-y` stays readline's.) (Copy mode built in [#234](https://github.com/Root-man/aiditor/issues/234): `C-c C-t` runs `vterm-copy-mode`, as vterm binds it, and toggles it. Entering sets the buffer's text, past read-only and without undo, to the scrollback then the screen, each row's trailing blanks trimmed, soft-wrapped rows joined into one line and blank rows below the cursor dropped, with point at the cursor, or the end of its line when the cursor sits past trimmed blanks. The text keeps each cell's colours, bold, italic and underline as faces, which gained those three attributes; to keep a coloured scrollback cheap to draw, a window of a buffer without folds scans only the properties near its lines. The mode line shows `[char]` after a terminal's name, without a position, or `[copy]` and point's position. Keys and typed text then run commands as in any read-only buffer and the window draws the text; output still feeds the grid but leaves the text alone. The `vterm-copy-mode` minor mode binds `RET` to `vterm-copy-mode-done`, which copies the active region, or point's line without its newline, to the kill ring and clipboard and leaves. Leaving empties the text, moves point to 0 and shows the live screen. Copy mode belongs to the buffer, as in Emacs, so every window showing it changes together.) (Prompt jumps built in [#245](https://github.com/Root-man/aiditor/issues/245): in copy mode `C-c C-p` (`vterm-previous-prompt`) and `C-c C-n` (`vterm-next-prompt`) move point to the previous or next command's input start, its `B` mark, else its `A`, with marks keeping their column so a jump lands after the prompt. Entering copy mode maps the marks into its text, wrapped rows joined, so output that arrives meanwhile doesn't move them. A count moves that many commands, stopping at the farthest; with none that way they echo `No prompt found`. They are not bound in char mode.) (Output selection built in [#246](https://github.com/Root-man/aiditor/issues/246): in copy mode `C-c C-r` (`vterm-mark-output`) sets an active region over the output of the command at point, the last whose prompt starts at or before point, so its command line counts too: from its `C` mark to its `D`, else the next prompt, else the text's end, without the newline ending its last line, with point at the start. `RET` then copies it. With no command at point, or one without `C`, it echoes `No command at point`.)

**`$EDITOR` in terminals.** Git runs in terminal buffers, so `git commit` and `git rebase -i` launch `$EDITOR`. Terminal buffers set `EDITOR` and `VISUAL` to a small client command, like `emacsclient`, that opens the file in a buffer in the terminal's workspace and blocks until you finish or abort the edit. The mechanism is to be decided (likely a Unix socket the editor listens on).

**App bundle** (built in [#266](https://github.com/Root-man/aiditor/issues/266)). `scripts/bundle.sh` builds the release binary and installs it for the current user. On macOS it installs `~/Applications/aiditor.app` (Info.plist with bundle id `io.github.root-man.aiditor` and name `aiditor`, an icon made from `crates/aiditor/resources/aiditor.png` with `sips` and `iconutil`, the binary in `Contents/MacOS`) and signs it ad hoc; there is no notarization. It is assembled in a temp dir and replaces an earlier install only once it is complete. On Linux it copies the binary to `~/.local/bin/aiditor` and installs `aiditor.desktop` (which runs that binary by absolute path) and the scalable icon under `$XDG_DATA_HOME`, `~/.local/share` by default; the window's app id is `aiditor`, matching the entry. `aiditor .` from a shell still runs the binary directly. The icon is a placeholder, kept as an SVG source and a 1024 px PNG.

**Process environment.** An app launched from the macOS Dock or a Linux desktop launcher does not get the shell's environment, so agents and formatters would not find `claude`, `codex`, `node`, `mix` or `cargo`, nor the asdf/mise shims behind `.tool-versions`.

(Decided in [#267](https://github.com/Root-man/aiditor/issues/267); capture built in [#268](https://github.com/Root-man/aiditor/issues/268): the markers are printed with `printf '\036…\036'`, so they are not in the command text bash also keeps in `BASH_EXECUTION_STRING`; reading stops at the end marker rather than at EOF, so a daemon the profile starts can't hold the capture; entries that are not UTF-8 are skipped; `SHELL` unset means `/bin/sh`; the timeout is 5 s. Captures start when a project first has a workspace, and each is noted in `*Messages*`, success or fallback. `project-capture-environment` re-captures the current workspace's project, which keeps its old environment until the answer, a later answer replacing an earlier one, and `getenv` echoes a variable from the current project's environment. Nothing waits for a capture yet, since agents and formatters don't exist; a project file changing its primary root keeps the old capture until re-captured.)

- **Launched from a shell** (`aiditor .`): use the inherited environment as is. The check is whether stdout is a terminal, as in Zed; a Dock or desktop-launcher start has none. A redirected shell launch (`aiditor . &>log`) captures anyway, which costs time but not correctness.
- **Otherwise:** capture the environment per project, in the background, when the project's first workspace opens; agent and formatter spawns wait for it. The capture runs the user's shell as an interactive login shell in the primary repo, in a new session with stdin from `/dev/null`: `$SHELL -l -i -c '<start marker>; env -0; <end marker>'`. Only what lies between the markers is read, so profile output before it and logout scripts after it are ignored; output is used even when the shell exits non-zero, and `SHLVL` is dropped. After a few seconds the process group is killed and the app's own environment is used, with a note in the Messages buffer. GNU and macOS `env` both support `-0`; one without it falls back the same way. A command re-captures it after you change your shell setup; running processes keep theirs.
- **direnv.** Its hooks, like `mise activate`'s, run at a prompt, which `-c` never draws. direnv is loaded separately, with `direnv export json` in the primary repo ([#270](https://github.com/Root-man/aiditor/issues/270)), as Zed does. (Built in [#270](https://github.com/Root-man/aiditor/issues/270): after a successful capture only, when `direnv` is on the captured `PATH`; it runs with the captured environment and `TERM=dumb`, its strings set variables and its `null`s unset them. A non-zero exit, such as a blocked `.envrc`, bad JSON or more than 30 s keeps the captured environment, with direnv's error in `*Messages*`. `.envrc` changes are picked up by `project-capture-environment`, and only the primary repo's is loaded.)
- **Overrides.** The agent registry's `env` goes on top of the captured environment and the project file's `env` on top of that, as a project file overrides global settings ([#194](https://github.com/Root-man/aiditor/issues/194)). (Project file `env` built in [#269](https://github.com/Root-man/aiditor/issues/269): it reaches terminals started with `vterm` as extra variables, on top of the editor's own environment and under the terminal's own variables, and `getenv` shows it on top of the captured or inherited value, at once even while a capture runs. Project commands leave the table alone; a hand edit applies to processes started after `C-x C-r`. A login shell's profile can still reassign a variable.)
- Terminal buffers start the user's shell as a login shell, which loads the profile itself (bash reads `.bash_profile`, falling back to `.bash_login` or `.profile`, rather than `.bashrc`); the captured environment matters most for agent processes and formatter commands.

**Language support.** Tree-sitter for highlighting, folding and structural motion in Elixir (with HEEx), Rust, JS/TS, YAML and Markdown. LSP comes after the MVP, one server per root and language. (Highlighting built for JS/TS in [#256](https://github.com/Root-man/aiditor/issues/256): visiting a `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts` or `.tsx` file parses it with that grammar (JavaScript, TypeScript or TSX), and the language is not picked again if the buffer later visits another file. Every text change applies `Tree::edit` in the buffer; the tree is reparsed incrementally on the core thread when a window next draws it, so a revert's many hunks cost one parse, as a `shortcut:` until parsing moves to the syntax service. The display builder runs the highlights query over the window's lines only and colours each char by its capture name from `theme.syntax`, a table of capture name to colour that `settings.toml` overrides key by key; a name without an entry takes its longest dotted prefix's. The innermost node wins, then the later pattern on one node, as Zed and Helix resolve them; JavaScript's query is its highlights and JSX queries, as its grammar parses JSX in `.js` files; TypeScript's is JavaScript's highlights followed by its own, and TSX's adds JSX's in between. Face properties and the region draw over syntax colours; highlights are not text properties. Not yet: injections (JSDoc, regexes), locals, bold or italic syntax faces.) (Built for Rust, Elixir, HEEx and YAML in [#257](https://github.com/Root-man/aiditor/issues/257): `.rs`, `.ex`, `.exs`, `.heex`, `.yml` and `.yaml` files use the crates.io grammars' own highlights queries, and `theme.syntax` gains `module` and `boolean`. An EEx template is highlighted by the extension before `.eex`, so Phoenix's `a.html.heex.eex` is HEEx and `a.ex.eex` Elixir; EEx tags in a language other than HEEx parse as errors. `~H` sigils stay one string until injections.) (Built for Markdown in [#258](https://github.com/Root-man/aiditor/issues/258): `.md` and `.markdown` files use `tree-sitter-md`'s block grammar and block query, so headings, code blocks, list and quote markers and thematic breaks are coloured, and `theme.syntax` gains `text.title`, `text.literal`, `text.uri`, `text.reference` and `punctuation.special`. Fenced code is drawn whole in the `text.literal` colour; the inline grammar (emphasis, code spans, links) and code in its fence's language wait for injections.) (Built for TOML in [#261](https://github.com/Root-man/aiditor/issues/261): `.toml` files use `tree-sitter-toml-ng`'s highlights query followed by one pattern that colours a pair's plain key as `property`, as the bundled query colours dotted keys, so only table header keys are `type`. No new `theme.syntax` entries.)

**Search and navigation.** File finder and grep across all project roots (ripgrep's library crates), fuzzy matching in the minibuffer, swiper-style line search in the buffer, and jump history. Grep-based jump to definition, jumping to `file:line` from terminal output, grep hits and agent tool calls, and editing grep results in place are in the MVP; their specs are to be decided. (Grep service built in [#73](https://github.com/Root-man/aiditor/issues/73): a search looks in the files the file index lists, roots in order and each root's files in path order, with `grep-searcher`. The pattern is one regexp in ripgrep's syntax with smart case, as consult-ripgrep passes `--smart-case`; an invalid one ends the search with its error. A file stops at its first NUL byte as binary, and unreadable files are skipped, both as `rg` does. Each hit carries its root, relative path, 0-based line, the char column of the line's first match and the line's text; hits reach the core as numbered `Msg::Grepped` batches, checking the roughly 50 ms deadline at each match as well as file completion; the last batch is marked done, up to the exact hit limit the core passes. A blocked read or match-free region has no intermediate-delivery guarantee. Starting a search or `GrepOp::Cancel` stops the running one between files or matches, and it sends nothing more. Not yet: truncating long lines, a parallel walk.) (Project grep built in [#74](https://github.com/Root-man/aiditor/issues/74), as consult-ripgrep: `project-grep` (`C-x p g`, project.el's key) prompts `Grep in <project>: ` and searches every root of the current workspace's project for the typed text as that regexp, once it has 3 chars and 200 ms passed since the last change (consult's `consult-async-min-input` and `consult-async-input-debounce`); shorter text cancels the search and empties the list. Hits are listed as `<root name>/<path>:<line>:<text>`, root names as the finder gives them, in the service's order and up to 10,000; the old list stays until the new search's first batch, so it does not flash empty while typing, and an invalid regexp echoes the last line of its error. The selected hit is previewed in the window the prompt was opened from at the start of its match, `RET` visits the file there (after its read, for a file no buffer visits), and closing the prompt cancels a running search. The typed text joins the prompt's `M-p` history as swiper's does. Not yet: consult's `#pattern#filter` and multi-word input, highlighting matches, a searching indicator; previewing a hit in an open buffer leaves that buffer's remembered point at the hit.) (Jump history built in [#76](https://github.com/Root-man/aiditor/issues/76), as Emacs 29's xref history: each workspace keeps a back list of up to 100 positions and a forward list, shared by its windows. Showing another buffer in the selected window (`C-x b`, `C-x 4 b`, `find-file`, `project-find-file`, a grep hit in another file), a grep hit in the current buffer and a swiper jump that moves point record the position they leave, as a marker that follows edits; previews record nothing, nor does repeating the newest position, and every jump empties the forward list. `M-,` (`xref-go-back`) goes to the newest back position in the selected window, putting the one it leaves on the forward list, and `C-M-,` (`xref-go-forward`) does the reverse; both skip positions in killed buffers and the one point is at, and say `At start of xref history` or `At end of xref history` when nothing is left. Not yet: `C-u M-,` clearing the history, a history per window, recording `M-<` or `M->`.)

**Git.** Nothing built in for the MVP: the git CLI runs in terminal buffers, and `git diff` there is how agent changes are reviewed.

**Persistence.** Only the agent session index survives a restart, in SQLite under the platform data dir (Application Support on macOS, `$XDG_DATA_HOME` on Linux). Workspaces, buffers and terminals start fresh on every launch, apart from crash recovery below. Project definitions and settings are TOML in the config dir.

**Crash safety** (proposed). Nothing but the session index is persisted, and an experimental editor will crash, so unsaved edits need a safety net.

- **Auto-save files.** About two seconds after the last edit, and at least every 30 seconds while a buffer is dirty, its text is written to a recovery dir under the platform data dir. Never next to the file, so repos, the file watcher, agents and `git status` never see it. Each recovery file records the original path, the hash of the disk version the buffer was based on, and the time. The core hands a copy of the rope to the persistence service (cheap: `ropey` ropes share their nodes), which writes it to a temp name and renames it. Saving, reverting or killing the buffer deletes the recovery file. Only buffers visiting a file are covered, as Emacs's `auto-save-default`; scratch, terminals and session buffers are not (scratch dropped after the M0 gate, [#54](https://github.com/Root-man/aiditor/issues/54)). (Built in [#50](https://github.com/Root-man/aiditor/issues/50): one 2-second idle timer, restarted by each key, and one 30-second timer started by the first key after a write, shared by all buffers. Covered means modified and visiting a file, so `*scratch*`, `*Messages*` and the minibuffer are skipped; a no-file recovery file from an earlier session can still be recovered and is then deleted. The dir is `recovery/` under the data dir, mode 0700; each file is `<pid>-<buffer number>`, a JSON header line (`name`, `path`, `hash`, `time` in Unix seconds) followed by the text with LF line endings. One service thread writes and deletes them in order. A buffer that is killed or no longer modified loses its file, and quitting normally deletes them all, since the user already chose to discard those edits. The file hash is FNV-1a 64, stable across Rust releases.)
- **Recovery on launch.** If recovery files exist, the editor opens a list of them. For each one you can open it as a dirty buffer holding the recovered text, compare it with the disk, or discard it. (Built in [#51](https://github.com/Root-man/aiditor/issues/51): the "list" is one minibuffer prompt per file, oldest first, `Recover auto-saved <path>? ` with `Yes`/`No` completion. `Yes` visits the file (or reuses the unmodified buffer of that name, for a buffer without one), replaces its text with the recovered text as one undoable edit and keeps the recorded disk hash, so `C-x C-s` refuses a file changed since. The text is auto-saved under the new session at once, and the old file deleted after it. `No` deletes the file; `C-g` keeps the rest, which `M-x recover-buffers` offers again. Files are read at launch before this session writes any, so a `.tmp` (a write cut short) is skipped, and a file named with this session's pid is never deleted through recovery. Compare with the disk by recovering the file, then `M-x diff-buffer-with-file` ([#82](https://github.com/Root-man/aiditor/issues/82)). Not yet: the auto-save time in the prompt, and telling a crashed session's files from those of another instance still running.) An end-to-end test ([#53](https://github.com/Root-man/aiditor/issues/53)) runs `aiditor-headless`, the core and services without GPUI driven by a key script: it edits a file, kills the process with SIGKILL once the recovery file is written, relaunches, accepts the recovery, saves and quits, then checks the file holds the edit and no recovery file is left.
- **Contain panics.** Each command runs under `catch_unwind`. A panicking command is logged to the Messages buffer with a backtrace, and the editor keeps running. The state that command touched may be inconsistent, and the log entry says so. The frontend also wraps every call into the core in `catch_unwind`: on macOS, keys are handled inside an Objective-C callback, where a panic aborts the process instead of unwinding. (Built in [#52](https://github.com/Root-man/aiditor/issues/52): the handler call is wrapped, so keys, `M-x` and prompt answers are all covered; the echo line says `<command> panicked; its state may be inconsistent (see *Messages*)` and `*Messages*` gets that line, the panic and a backtrace, captured by a panic hook the core chains once. The core fails to compile with `panic = "abort"`, and CI also greps the manifests for it, since CI never builds the release profile. Not yet: the frontend wrapper, so a panic outside a command still ends the process.)

**Frontend.** A native GUI built on GPUI, targeting macOS and also running on Linux for development; one frame only. The core produces a display model: per window, the visible lines (each with its own height) with styled spans, folds (invisible ranges with a placeholder), whole-line decorations, cursors and overlays. Positions come from shaped lines, not a cell grid (the frontend shapes each display line whole and draws the cursor over it at point's x offset, so moving point never moves text; since #54 the cursor is a block, the char under it in the background color, and the frame keeps an 8 px gap at the sides, Emacs's fringe width, and 2 px at the bottom so macOS's rounded corners never clip text), so a face can later carry its own font and size; the frontend draws it and feeds input events back. Keeping that boundary means the frontend stays thin and the core is testable without it. (Emoji, [#237](https://github.com/Root-man/aiditor/issues/237): GPUI 0.2.2 on Linux rasterizes with swash, which draws colour bitmaps and COLR v0 layers but not COLRv1, still so in Zed master. Fedora's only colour emoji font, `Noto-COLRv1.ttf`, drew every emoji blank, in buffers and terminals alike. At start the frontend asks `fc-match` for `Noto Color Emoji`'s file; if it has COLR with no v0 glyphs and no CBDT or sbix, it resolves that family by name, which GPUI's `load_family` answers by removing the face, as it does any face without an `m`. Emoji then fall back to whichever installed font has them, monochrome Noto Emoji (`google-noto-emoji-fonts`) or Symbola, in the text's colour. Colour emoji GPUI can draw, Apple Color Emoji or CBDT Noto Color Emoji, are untouched. A monochrome emoji font can't be named in a run either: the same removal drops it. In a terminal an emoji is a wide char, a run of two cells.)

**Runtime.** Tokio for the async services, on background threads. The core runs on GPUI's main thread; see below.

## Core thread and output floods

### The core runs on the UI thread

GPUI does not run on Tokio. It has its own executors: a foreground executor on the main thread, where all UI code and rendering run, and a background thread pool. The core runs on that main thread.

- **The core is a plain Rust crate** with no GPUI dependency, written as a state machine: `handle(&mut Core, now, Msg) -> Effects`. The caller passes the time, so the core never reads the clock. Tests drive that function directly, without a frontend, on a fake clock.
- **Timers live in the core** as deadlines, each carrying the message it delivers. Due timers fire on every `handle`; the app keeps one GPUI timer armed for `next_deadline()` and wakes the core with `Msg::Tick` when it passes.
- **The frontend holds the core** and calls it directly for each input event. Rendering reads core state directly; the display model is not copied across threads.
- **Services run on a Tokio runtime** on background threads. Their results arrive on channels that a GPUI foreground task drains into the core.
- **Slow work belongs in services.** Filesystem reads, prepared preview text, configuration loading, indexing, grep and large diffs run away from the UI thread; fuzzy completion uses its own workers. Configuration parsing/application and Swiper's full line scan remain synchronous core work, so very large inputs can still delay the UI.
- **Text input and layout are answered synchronously.** GPUI asks the focused view for text ranges, the selection and character positions during IME input, and scrolling uses GPUI's text layout directly; soft wrap is in the core, in char columns, like the horizontal scroll.

This is the same shape as Zed, so GPUI's examples and Zed's code apply directly. The alternative, a core on its own thread that sends a display model to the frontend after each change, was rejected: every keystroke would cross threads twice, the core could not measure text, and the frontend would have to mirror the focused buffer's text and selection to answer IME queries.

### Output floods

A build or a `cat` of a large file can produce megabytes per second of terminal output, and agents stream many small updates. If every chunk is a separate message and every message triggers a redraw, typing lags. Three rules prevent that:

- **One redraw per frame at most.** A change marks the view dirty; GPUI renders once per frame.
- **Batched reads.** The PTY reader reads whatever is available (up to about 64 KB) and sends one message per batch.
- **Bounded channels.** Each terminal has its own channel, four batches deep, separate from the shared service channel. If the core falls behind, only that terminal's reader stops reading, its kernel PTY buffer fills, and its producing program blocks; other terminals and service replies keep flowing. That is the usual terminal flow control, and it caps memory.

Agent streams need nothing more than that: ACP updates are small and slow compared with PTY output. Re-render only the message being streamed, not the whole transcript.

**The terminal emulator lives in the core.** The PTY task sends raw byte batches, and the core feeds them into the `alacritty_terminal` grid it owns. There is no shared state, copy mode and search read the grid directly, and tests feed bytes and snapshot the grid. The cost is that VT parsing runs on the UI thread, so a sustained flood can compete with typing.

The emulator sits behind a terminal interface so it can move later. If typing lags during a flood (check by running `yes`, or `cat` on a large file, in one terminal while typing in another buffer), move the emulator into the terminal task behind a lock, as Zed and Alacritty do. That takes parsing off the UI thread at the cost of shared mutable state, the one exception principle 4 would then allow. (Checked in [#226](https://github.com/Root-man/aiditor/issues/226): the emulator stays in the core. The core benchmarks parse one 64 KB batch in about 0.6 ms (`yes` 0.62 ms, a `cat` of text lines 0.59 ms, about 100 MB/s) and build a 50x120 screen's runs in 0.1 ms, on a Linux desktop. The flood did starve the UI, though not through parsing: Tokio's `recv` never pends while messages queue, so the app's drain task handled batch after batch without giving GPUI a turn, and keys and frames stopped. The drain now yields to the executor after each message, as Zed's terminal does. With that, typing in a file buffer during `yes` and a looping `cat` of a 38 MB file showed no visible lag on Linux: 150+ fps, with render, shape, core and Tokio tick each under 1 ms. macOS is checked at the M2 gate.) (Grid built in [#223](https://github.com/Root-man/aiditor/issues/223): `alacritty_terminal` 0.26, behind a `Terminal` that is fed bytes, returns the replies and reads its screen, with alacritty's default 10,000 lines of scrollback. A terminal buffer's content is the grid; it is read-only and its text is an empty rope, and even the edits that pass read-only, like `*Messages*`'s appends, refuse it. The core maps each `TerminalId` to its buffer and feeds `Msg::TerminalOutput` into the grid; the replies the emulator writes back, such as cursor position and device attribute reports, go out as one `TerminalOp::Write` after the batch. Title, bell, clipboard, color and text-area-size requests are ignored, as is output for an unknown terminal or a killed buffer.) (Drawing built in [#225](https://github.com/Root-man/aiditor/issues/225): a terminal window shows the live screen, not the scrollback. The core turns each row into runs of one style at their grid columns, a wide char a run of its own, with colours resolved there: ANSI 0 to 15 from the theme's `ansi` palette unless OSC 4 set them, the xterm cube and gray ramp, truecolor exact, inverse swapping, dim at 2/3. The frontend shapes each run with every glyph advancing one cell and places it at column × cell width, as Zed's terminal element does. The cursor is a block, beam or underline as DECSCUSR sets it, absent while hidden, and a hollow block in a window that isn't selected. Not drawn: strikethrough, undercurl and other underline styles beyond a plain one, and concealed text.) (Terminal buffers built in [#224](https://github.com/Root-man/aiditor/issues/224): `M-x vterm` spawns the login shell in `vterm<n><workspace>`, `n` the smallest free number from 1, shown in the selected window and started in the current file's directory, a terminal buffer's cwd, or the project's primary root. After every message the core sends `TerminalOp::Kill` for each terminal whose buffer was killed, by any path, and sizes each live terminal to the smallest window of the current workspace showing it, rows and columns taken separately as Emacs's `window-adjust-process-window-size-smallest`, resizing the grid and sending `TerminalOp::Resize` when that changes; a terminal no window shows keeps its size, and one opened before the frame size is known starts at 24x80. The shell's exit kills its buffer silently; a spawn failure kills it and echoes the reason. Either way the core sends the terminal one `TerminalOp::Kill`, which signals nothing for a shell that is gone or never started, so the service releases its PTY and input thread at once rather than at quit. `kill-buffer` asks `Buffer <name> has a running process; kill it? ` (`no`, `yes`), and quitting asks `Active processes exist; kill them and exit anyway? ` (`No`, `Yes`) after the modified-buffer questions and before their saves start; declining still saves the buffers answered `Yes`. Killing a workspace kills its terminals without asking. Not yet: `rename-buffer`, sizing from an inactive workspace's windows.)

### Fake agent script

Decided in [#285](https://github.com/Root-man/aiditor/issues/285). `aiditor-fake-agent` (a binary of `aiditor-services`) runs the JSON script that `AIDITOR_FAKE_AGENT` names, relative to its working directory; without it the script is empty, and a script that doesn't parse exits with code 2 and the reason on stderr. It always reports `pid=`, the advertised `fs.readTextFile`/`fs.writeTextFile`/`terminal` capabilities, `cwd=` and `A=` on stderr, and answers `session/new` with session `fake-session` and one config option, the select `mode` (category `mode`) with values `auto` (current) and `plan`.

```json
{
  "session": [{"stderr": "ready"}],
  "prompts": [
    [
      {"update": {"sessionUpdate": "agent_message_chunk", "content": {"type": "text", "text": "hi"}}},
      {"permission": {"toolCall": {"toolCallId": "call-1"},
                      "options": [{"optionId": "allow", "name": "Allow", "kind": "allow_once"}]}},
      {"write": {"path": "src/a.rs", "text": "fn main() {}\n"}},
      {"stop": "end_turn"}
    ]
  ]
}
```

`session` runs once after `session/new` is answered; the n-th `session/prompt` runs the n-th list of `prompts`, and a turn that runs out of steps, or a prompt past the end, ends with `end_turn`. Steps run in order:

| Step | Does |
| --- | --- |
| `{"update": <SessionUpdate>}` | Sends a `session/update` with the update as ACP JSON, so any update the schema has works |
| `{"permission": {"toolCall": ..., "options": [...]}}` | Sends `session/request_permission`, waits, then writes `permission answered: <outcome JSON>` or `permission error: <message>` to stderr |
| `{"write": {"path": ..., "text": ...}}` | Writes the file relative to the session's `cwd`, creating parent directories; `write error: ...` on stderr if it fails |
| `{"sleep": <ms>}` | Waits |
| `{"stderr": <line>}` | Writes the line to stderr |
| `{"exit": <code>}` | Exits at once; ACP messages not yet written are lost, so `sleep` first when they matter |
| `{"stop": <StopReason>}` | Ends the turn with that reason (`end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`), skipping the rest |
| `"ignoreSigterm"` | Ignores SIGTERM from then on |

`session/set_config_option` setting `mode` to `auto` or `plan` answers with the options and sends a `config_option_update`; any other option or value is an invalid-params error. `session/cancel` ends the running turn at once, even mid-`sleep` or mid-`permission`, with `cancelled`. Terminals are added with the agent terminals epic if [#100](https://github.com/Root-man/aiditor/issues/100) finds the adapters use them.

Optional release-mode benchmarks cover core editing, syntax parsing/highlighting, display, completion, reverts and terminals, plus warm-cache indexing and grep services. An explicit local GUI suite measures scheduled synthetic input through matching frame paint during terminal floods. A manually started Actions workflow retains results and compares compatible previous runs, with an optional PR comment; see [Performance benchmarks](performance.md). Timings are informational, not CI gates.

### Recorded transcripts

Recorded in [#286](https://github.com/Root-man/aiditor/issues/286). `aiditor-acp-record OUT -- COMMAND [ARGS...]` (a binary of `aiditor-services`) runs an agent with its stdio passed through unchanged and appends every line to OUT as `{"from": "client" | "agent", "message": ...}`; it goes in front of any agent with a registry entry. `crates/aiditor-services/tests/transcripts/` holds a Claude Code and a Codex session recorded through the agent service with aiditor's capabilities, every agent request refused as the core does, and scrubbed (`{cwd}`, `{home}`, emails, the advertised commands cut to three); its README says how to record and scrub them again. Claude's adapter starts in `default`, so its edit asks permission, and it enters plan mode itself with a `current_mode_update`; Codex is started in `workspace-write`, as its default `agent` mode lets a reviewer model approve instead of the client, and it never changes its own mode.

Replayed in [#287](https://github.com/Root-man/aiditor/issues/287). With `AIDITOR_FAKE_AGENT_REPLAY` naming a transcript, `aiditor-fake-agent` replays it instead of a script: it writes the agent messages recorded before the next client message, then reads one client message and checks it against that one. Requests and notifications match by method and responses by id; agent responses get the live client request's id, and `{cwd}` becomes the live `session/new` `cwd`. A message the transcript doesn't expect makes it write `unexpected client message: <message>` and what it expected to stderr and exit 1; a bad transcript exits 2. `committed_transcripts_replay_through_the_core` in `tests/transcripts.rs` replays each committed transcript through the agent service into the core, starting it with `agent-start` and typing the recorded prompts, and asserts every `session/update` reaches the core typed, every agent request is answered and every turn ends with its recorded stop reason. Later epics add their assertions, such as a session buffer snapshot or permission answers, to that test.

## Milestone path

Build the editor core first and add the agent at M3, so agent features land on a model that already works. Each phase ends with a gate you can test by using it.

| Phase | Scope | Gate |
| --- | --- | --- |
| M0 · Skeleton | Rope buffers, undo; window splits, keymap trie; minibuffer, find-file, save; auto-save and recovery | Edit and save a file using Emacs keys only |
| M1 · Projects + workspaces | Primary repo + extra roots, project commands; finder + grep across repos; workspaces with their own layouts and buffers | In two workspaces on different projects, find a file from an additional root, grep across two roots and jump to a hit, then keep editing while an external write auto-reverts another open buffer |
| M2 · Terminal | PTY + VT emulator buffers; char mode and copy mode; shell integration marks | Run the test suite and make a git commit in a terminal buffer |
| M3 · First agent | Claude Code via ACP; session buffer (with soft wrap) and modes; process environment; agent terminals as buffers (if the adapter uses `terminal/create`) | Land one real change with an agent, in the editor |
| M4 · Sessions | Resume after restart via `session/load`; Claude + Codex side by side; extra roots, project preamble | One session makes a change across two repos |
| M5 · Polish | Tree-sitter for 5 languages, TAB indentation, formatter commands; registers, macros; grep-based jump to definition, `file:line` jumps, editable grep results; `$EDITOR` client for terminals | Daily driver for real work, without LSP (knowingly deferred) |

Phases are in order of dependency, not to scale; no dates are set. LSP, multiple cursors, ACP prompt features (`@file`, slash commands, image paste, tool-call diffs), block rows and proportional faces in the session buffer, agent status in the mode line, a dashboard with notifications, diff review, dired and worktree workflows come after M5.
