# Performance refactor scan, 2026-10-25

Based on `scripts/bench_local.py` (core, services and `--suite ui`) run on two machines:

- **macOS:** Apple M5 Pro
- **Linux:** AMD Ryzen 7 5800X3D (96 MB L3), Fedora, gcc 16

**Scope:** whole repo, weighted toward the benchmark's hot paths. macOS grep slowness (`grep/10k-hits-two-roots-complete-warm-cache`: 947 ms on macOS vs 85 ms on Linux) is excluded and handled separately on a Mac.

## Benchmark comparison summary

Pure CPU work is 2–2.6× slower on Linux, which matches the single-core gap. The outliers:

| Bench | macOS | Linux | Note |
|---|---|---|---|
| `grep/10k-hits-two-roots-complete-warm-cache` | 947 ms | 85 ms | macOS 11× slower; delegated |
| `index/10k-files-two-roots-warm-cache` | 28.3 ms | 16.5 ms | macOS slower |
| `syntax-load/ex/10000-lines-warm-grammar` | 33.5 ms | 141.8 ms | Linux 4.2×; other grammars 2.1–2.5× |
| `syntax-edit-frame/rs/100000-lines-character-undo-pair` | 72.7 ms | 76.8 ms | parity; macOS scales 19× from 10k, Linux 9× |
| `revert-apply-frame/rs/*` | 31–43 ms | 37–47 ms | only 1.1–1.2× |
| `grep/first-batch-two-roots-warm-cache` | 50.2 ms | 50.4 ms | equals the 50 ms `BATCH` deadline |
| GUI `yes` bytes in ~7 s | 429 MB | 51 MB | Linux ~7.5 MB/s |
| GUI `cat` bytes in ~7 s | 500 MB | 293 MB | |
| GUI `yes` input-to-paint p50 / p95 | 8.3 / 8.6 ms | 5.6 / 12.3 ms | displays differ: 120 Hz vs ~144 Hz |

## Explained without code changes

- **Linux `yes` at 7.5 MB/s is the kernel PTY ceiling.** A bare Python reader in a tight loop on a raw PTY gets `yes` at 7.7 MB/s (26-byte reads) and `cat` at 53.5 MB/s. aiditor gets 7.5 and 43 MB/s, so it already runs close to that ceiling.
- **`syntax-load/ex` 4.2× on Linux is hardware.** Elixir's generated `ts_lex` is 83 KB of machine code (Rust's is 17 KB). That overflows Zen 3's 32 KB L1 instruction cache and fits Apple's larger one. gcc `-O1`, `-O2` and `-Os` and tcmalloc all left a standalone parse at ~140 ms, so build flags and the allocator are not the cause.
- **macOS 19× scaling from 10k to 100k lines (Linux 9×)** fits the 5800X3D's 96 MB L3 holding the whole 100k-node tree; see row 5.

**#2:** `terminal-copy/colored/10k-lines-display` takes 3.96 ms per frame on Linux and 2.27 ms on macOS. The plain version takes 96 µs. The scroll pair costs 7.9 ms, more than one 144 Hz frame.

**#3:** the comment-delimiter pair measures 42 ms at 10k lines and 445 ms at 100k on Linux (17.7 ms and 186 ms on macOS). Each keystroke that reparses everything after it stalls drawing for that long.

**#5:** the same tree shape is why `revert-apply-frame/rs` costs about the same for 1 hunk and for 1,000 (37 vs 47 ms on Linux). The time goes into the single reparse, not the edits.

The structural pass found nothing worth a row. The largest files are mostly tests, and none has more than about 900 lines of non-test code with mixed jobs.

**Start with:** row 1, a one-line change plus a test update that removes 50 ms from every grep and makes its benchmark mean something. Then row 2, which removes the worst per-frame cost in the suite.

**Not checked:** the GUI bench wasn't rerun, so the Linux p95 input-to-paint of 12.3 ms under load has no row yet; it needs a trace with `--debug` stats. No clang build (not installed on the Linux box). minibuffer, visiting, project_commands and watcher weren't read beyond their sizes. The number of properties in the coloured copy-mode fixture wasn't counted.
